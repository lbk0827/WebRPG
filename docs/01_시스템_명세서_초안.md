## 0. 클린룸 원칙 (모든 작업의 전제)

원본은 `_Reference_ReadOnly/` 에 격리되어 있으며 **상업적 이용이 금지**되어 있다.
따라서 우리는 다음 원칙을 지킨다.

| 구분 | 판단 | 근거 |
|---|---|---|
| 게임 규칙·시스템·메커니즘 | ✅ 참고 가능 | 저작권은 아이디어를 보호하지 않음 |
| 수학적 계산 구조 (예: "속도의 제곱근에 비례") | ✅ 참고 가능 | 수식·알고리즘 자체는 표현이 아님 |
| 소스 코드 (구조, 변수명, 함수명 포함) | ❌ 금지 | 어문저작물로서의 표현 |
| 밸런스 데이터 테이블 전체 | ❌ 금지 | 편집저작물(선택·배열·구성)로 보호될 소지 |
| 고유명사 세트 (스킬/아이템/몬스터/직업명) | ❌ 금지 | 표현 + 식별력 |
| 텍스트(튜토리얼, 설명문, 전투 메시지) | ❌ 금지 | 어문저작물 |
| 이미지·아이콘·CSS 디자인 | ❌ 금지 | 미술저작물, 다수는 제3자 소재 |
| "Hall of Fame" / "HOF" 명칭 | ❌ 금지 | 상표·부정경쟁 리스크 |

**본 문서에 등장하는 숫자는 전부 "원본 관찰값"이며 참고용이다. 우리 게임의 실제 값은 3장 이후에 새로 설계한다.**

## 1. 게임 개요

### 1.1 한 줄 정의

> 플레이어는 전투를 직접 조작하지 않는다. **전투 전에 캐릭터별 "행동 규칙"을 프로그래밍**하고,
> 그 규칙이 얼마나 잘 짜였는지를 자동 전투 결과로 검증받는 육성 게임.

### 1.2 코어 판타지

"내가 짠 전술이 스스로 굴러가서 이기는 쾌감."
플레이어의 실력은 **반사신경이 아니라 설계 능력**으로 측정된다.
이것이 이 장르의 유일무이한 축이며, 우리 게임의 정체성도 여기에 둔다.

### 1.3 장르 좌표

- 비동기 웹 RPG / 오토배틀러 / 파티 빌딩 / 전술 프로그래밍
- 인접 레퍼런스: 파이널 판타지 12의 감빗(Gambit), Zachtronics류 프로그래밍 퍼즐, 오토체스의 관전성
- **차별점**: 오토체스는 배치만, 감빗은 조연 시스템. 여기서는 **규칙 편집이 게임의 전부**다.

### 1.4 코어 루프

```
[1] 파티 편성 & 행동 규칙 작성
        ↓
[2] 지역 선택 → 자동 전투 실행 (행동력 소모)
        ↓
[3] 전투 로그 관전 → 패턴의 결함 발견
        ↓
[4] 보상 획득 (경험치 / 재화 / 재료)
        ↓
[5] 레벨업·전직·스킬 습득 / 장비 제작·강화
        ↓
[6] 규칙 수정 → [1] 로 복귀
        ↓
[7] (주기적) 콜로세움 랭킹 도전 · 협동 레이드
```

**핵심**: [3]의 "로그를 읽고 원인을 찾는" 단계가 이 게임의 진짜 게임플레이다.
전투 로그의 가독성 = 게임의 재미. 이 점을 UX 최우선 과제로 삼는다.

## 2. 관찰 기록 — 원본이 채택한 시스템들

각 항목은 `[관찰]` (원본이 무엇을 했는가) → `[평가]` (좋은가/나쁜가) 순서로 기술한다.

### S1. 행동력(Time) 경제 — 세션 제한

**[관찰]**

- 플레이어는 스태미나 성격의 자원을 가진다. 상한이 있고 실시간으로 회복된다.
- 일반 전투 1회에 큰 폭, 협동 레이드 1회에 아주 적은 폭을 소모한다.
- 원본 관찰값: 상한 1000, 1일 회복 총량 6000, 일반 전투 100 소모, 레이드 10 소모, 시작 시 900 보유.
  → 하루 약 60회 전투. 캡은 10회분뿐이므로 하루 여러 번 접속을 유도하는 설계.
- 회복은 "마지막 접속 시각과 현재 시각의 차이"를 회복량으로 환산하는 lazy 방식. 서버 타이머 없음.

**[평가]**

- lazy 회복은 서버 부하가 없고 정확하다. **이 구조는 그대로 채택할 가치가 있다.**
- 다만 캡이 10회분은 오프라인 손실이 크다. 상한을 더 넉넉히 잡아야 한다.
- 상업화 시 이 축이 곧 과금 지점이 되므로 **P2W로 흐르지 않게 설계**해야 함(3.3 참조).

---

### S2. 캐릭터와 스탯

**[관찰]**

- 유저는 여러 캐릭터를 보유(관찰값: 최대 10명)하고, 그 중 **5명을 편성**해 전투한다.
- 1차 스탯 5종: 힘 / 지능 / 손재주 / 속도 / 운
- 파생 스탯: 최대HP, 최대SP, 물리공격, 마법공격, 물리방어, 마법방어
- HP/SP는 직업별 **계수(coefficient)** 를 곱해 산출. 예: 근접 계열은 HP 계수가 높고 SP 계수가 낮음.
- 레벨업 시 **스탯 포인트**와 **스킬 포인트**를 별도로 지급 (관찰값: 각 5, 2). 자동 분배 없음 = 전부 수동 빌드.
- 스탯에는 개별 상한이 있음 (관찰값: 250).
- 최대 레벨 존재 (관찰값: 50). 필요 경험치는 저레벨 구간 2차식, 중간 구간 3차식,
  마지막 10레벨은 **하드코딩된 급증 곡선**(사실상 엔드게임 장벽).
- 전투 중 스탯 증감에도 상한이 있다(초기값 대비 배수 캡) → 버프 중첩으로 인한 수치 폭주 차단.

**[평가]**

- 스탯/스킬 포인트 분리는 좋다. "강해지는 축"과 "할 수 있는 일이 늘어나는 축"이 분리됨.
- 스탯 상한은 빌드 다양성을 강제하는 좋은 장치.
- 버프 상한(초기값 대비 배수)은 자동 전투에서 필수적인 안전장치다. **채택.**
- 마지막 구간 경험치 하드코딩은 조잡하다. 우리는 **단일 연속 곡선**으로 간다.

### S3. 직업과 전직

**[관찰]**

- 4개 1차 직업 계통(근접 / 마법 / 신성 / 원거리), 각 계통마다 2~3개의 2차 직업. 총 15개.
- 2차 전직 조건: **특정 레벨 이상 + 특정 1차 직업**. 조건 레벨은 직업마다 다름(관찰값 19~24).
  → 강한 상위직일수록 늦게 열려서, "언제 전직할지"가 선택이 된다.
- 직업은 세 가지를 결정한다: ① 장착 가능 장비 타입 ② HP/SP 계수 ③ 스킬트리 분기
- 2차 직업에서 더 이상의 전직은 없음(2단 트리로 종료).
- 성별에 따라 직업 표기명과 이미지가 갈린다.

**[평가]**

- "전직 레벨 조건이 직업마다 다르다"는 아이디어가 좋다. 균일하면 선택이 아니라 대기가 된다.
- 2단 트리는 얕다. 우리는 **3단 또는 서브클래스 조합**으로 깊이를 확보할 여지가 있다.

### S4. 스킬과 스킬트리

**[관찰]**

- 스킬은 선행 스킬을 습득해야 열리는 **의존 그래프**. 트리보다 DAG에 가깝다.
- 같은 선행 스킬에서 여러 갈래가 뻗고, 일부 갈래는 특정 2차 직업에서만 열린다.
- 스킬 하나가 갖는 속성:
  - 소모 SP / 물리·마법 구분 / 습득 비용(스킬 포인트)
  - **대상 지정**: `(진영, 범위, 횟수)` 3튜플
    - 진영 = 아군 / 적군 / 전체 / 자신
    - 범위 = 단일(individual) / 다수(multi) / 전원(all)
    - 횟수 = 타격 반복 수
    - 조합 예:
      - `(적, 단일, 3)` = 적 1명을 3회 타격
      - `(적, 다수, 4)` = 적 중 4명을 무작위로 1회씩 (중복 선택 가능)
      - `(적, 전원, 2)` = 적 전원을 2회씩
      - `(전체, 단일, 5)` = 아군·적군을 통틀어 아무나 1명을 5회
  - **위력 배율** (100 = 기본 1.0배)
  - **선딜/후딜** `(charge, stiff)` 2튜플 — 시전 준비 시간과 시전 후 경직
  - **커버 무시** 플래그 (후열 보호를 뚫음)
  - **지원기** 플래그 (아군 대상이므로 커버 판정에서 제외)
  - **타겟 우선순위**: 낮은HP비율 / 후열 / 전사자 / 소환수 / 시전 중인 적
  - **부가 효과**: 스탯 증감, 방어 관통, 독, 소환, 넉백, 강제 이동, 행동 게이지 조작 등
  - **무기 제한** (예: 활 전용)
- 복잡한 스킬은 데이터로 표현하지 못하고 별도 로직 파일에 직접 코딩되어 있다.

**[평가]**

- **`(진영, 범위, 횟수)` 3튜플은 매우 우아한 추상화다.** 이 아이디어는 반드시 계승한다.
- **선딜/후딜 분리**도 훌륭하다. "강한 기술은 준비가 길다"를 데이터만으로 표현 가능.
- 반면 "복잡한 스킬은 코드로 하드코딩"은 명백한 설계 실패. 스킬 하나 추가에 코드를 건드려야 한다.
  → 우리는 **효과를 데이터로 조합하는 이펙트 DSL**로 설계한다. 이게 큰 개선점이다.

### S5. 행동 패턴 AI ★ 이 게임의 심장

**[관찰]**

- 캐릭터마다 **순서가 있는 규칙 목록**을 가진다. 각 행은 `(조건, 행동)` 쌍.
- 자기 차례가 오면 **위에서부터 순서대로 조건을 평가**하고, **처음으로 참이 되는 행의 행동을 실행**한다.
  (= if / else-if 체인)
- 모든 조건이 거짓이면 그 캐릭터는 **아무것도 못 하고 차례를 넘긴다**.
  → "패턴 끝까지 조건이 안 맞으면 멍하니 서 있는다"는 것 자체가 페널티이자 학습 장치.
- **복합 조건(AND)** 지원: 특수 연결자를 쓰면 다음 행과 묶여 여러 조건을 동시에 만족해야 발동.
- 조건 카테고리 — 원본이 제공하는 판단 재료 전체:

| 카테고리 | 판단 가능한 것 |
|---|---|
| 자신 자원 | 자신 HP/SP의 절대값·비율(이상/이하), 자신 최대HP/SP |
| 아군 자원 | 아군 중 HP/SP가 N% 이하인 자가 존재, 아군 평균 HP/SP |
| 능력치 | 자신의 힘·지능·손재주·속도·운·물공·마공·물방·마방 (이상/이하) |
| 생존 | 아군/적군의 생존자 수, 전사자 수, 아군 전열 생존자 수 |
| 시전 상태 | 아군/적군 중 준비동작 중인 인원 수, 시전 중인 인원 수, 둘의 합 |
| 상태이상 | 자신의 중독 여부, 아군/적군 중독자 수 및 비율 |
| 진형 | 자신의 전열/후열 여부, 아군/적군의 전열·후열 인원 수 |
| 소환물 | 아군/적군 소환수 마릿수 |
| 필드 | 아군/적군 진영의 마법진 개수 |
| 행동 이력 | 자신의 누적 행동 횟수(이상/이하/정확히 N회째) |
| 횟수 제한 | "N회만 반드시" (1회성 오프너 지정용) |
| 확률 | "N% 확률로" |
| 특수 | 적 팀에 레벨 N 이상이 존재 |
| 무조건 | 항상 참 (fallback 행) |

- 조건에는 대부분 플레이어가 임의의 **수치(임계값)** 를 입력한다.
- 규칙 편집 UI가 별도 화면으로 존재하며, 몬스터 패턴 편집용 관리 도구도 따로 있다.

**[평가]**

- **이 시스템 하나가 게임의 존재 이유다.** 조건 목록의 폭이 곧 전략 공간의 크기.
- 우수한 설계 판단들:
  - 절대값과 비율(%)을 둘 다 제공 → "HP 200 이하"와 "HP 30% 이하"는 완전히 다른 전술이 된다
  - **"적이 시전 중" 조건** → 카운터 플레이가 성립. 이게 없으면 선딜 시스템이 무의미해진다
  - "N회째 행동" / "N회만" → 오프닝 무브 지정 가능
  - "확률로" → 상대가 내 패턴을 완전히 읽지 못하게 하는 노이즈
  - "아군 평균 HP" 같은 **집계 조건** → 개별이 아닌 전황 판단이 가능
- 한계:
  - **AND만 있고 OR / NOT이 없다.** 조건 표현력이 제한적.
  - 조건이 정수 ID 기반의 거대한 분기문으로 구현되어 있어 확장이 고통스럽다.
  - **패턴을 저장·공유·복제하는 기능이 없다.** 캐릭터마다 처음부터 다시 짜야 함 → 최악의 UX.
  - 시뮬레이션/디버깅 도구가 없다. 실제 전투를 돌려봐야만 검증 가능(= 행동력 소모).

→ **이 세 가지 한계를 해결하는 것이 우리 게임의 가장 큰 차별점이 될 수 있다.**

### S6. 전투 엔진

#### S6.1 행동 순서 — ATB 게이지

**[관찰]**

- 턴제가 아니라 **게이지 방식**. 각 캐릭터는 0에서 100까지 차오르는 게이지를 갖고, 100 도달 시 행동.
- 충전 속도는 **속도 스탯의 제곱근에 상수를 더한 값**.
  → 제곱근이므로 속도 투자에 **수확 체감**이 걸린다. 속도 극단 빌드를 자연히 억제. 좋은 설계.
- 매 스텝마다 "가장 먼저 100에 도달할 캐릭터"를 계산하고, 그 시점까지 전원의 게이지를 한 번에 진행시킨다.
  → 1틱씩 도는 게 아니라 **다음 이벤트로 점프**하는 방식. 계산이 가볍다.
- 동시 도달 시 무작위 선택.
- 스킬로 게이지 조작 가능: 지연(후퇴) / 가속(전진) / 즉시 행동.
- 원본에는 구·신 두 가지 계산 방식이 플래그로 공존한다(레거시 잔재).

**[평가]**

- 제곱근 체감 + 이벤트 점프는 둘 다 좋은 판단. **채택.**
- 다만 게이지가 실수형이라 **부동소수점 재현성 문제**가 있다.
  우리는 **정수 고정소수점**으로 간다. 비동기 PvP에서 리플레이가 일치하려면 결정론이 필수다.

#### S6.2 진형과 커버

**[관찰]**

- 캐릭터는 **전열 / 후열** 두 줄 중 하나에 배치된다.
- 후열이 공격 대상이 되면, **살아있는 전열 아군이 대신 맞아줄 수 있다** (커버).
- 커버 여부는 캐릭터별 **방어 성향** 설정으로 결정:
  항상 / 절대 안 함 / 자기 HP가 25·50·75% 초과일 때만 / 25·50·75% 확률로
- 커버 후보는 무작위로 섞은 뒤 앞에서부터 판정 → 특정 인원에게 커버가 몰리지 않는다.
- HP가 1 이하인 전열은 커버 불가 (다단히트로 죽어가며 계속 막는 문제를 막은 흔적).
- 커버 무시 플래그가 붙은 스킬은 후열을 직격한다.

**[평가]**

- **방어 성향을 캐릭터별 설정으로 뺀 것이 핵심 아이디어다.** 이것도 일종의 규칙 프로그래밍이며,
  S5의 패턴 시스템과 철학이 일치한다.
- 2열은 단순해서 좋다. 3열 이상으로 늘릴 이유는 아직 없다.

#### S6.3 타겟 선정

**[관찰]**

- 스킬에 지정된 우선순위에 따라 후보 중 1명을 고른다:
  HP비율 최저 / 후열 우선 / 전사자 / 소환수 / 시전 중인 적
- **중요한 구분**: 우선순위는 두 종류다.
  - *선호형* (HP최저, 후열): 해당 대상이 없으면 아무나 고름 → 스킬은 반드시 발동
  - *한정형* (전사자, 소환수, 시전 중): 해당 대상이 없으면 **스킬 사용 자체가 실패**
  → 부활기를 죽은 사람이 없을 때 헛되이 쓰지 않게 하는 장치.
- 우선순위 미지정 시 생존자 중 무작위.

**[평가]**

- 선호형/한정형 구분은 섬세하고 옳다. **채택.**

#### S6.4 데미지

**[관찰]**

- 물리: `√(힘) × 상수 + 장비 물리공격력` / 마법: `√(지능) × 상수 + 장비 마법공격력`
  (일부 스킬은 힘 대신 손재주를 참조하도록 지정할 수 있다)
- 여기에 스킬 위력 배율을 곱한다.
- 방어는 **2단 적용**: 먼저 비율 감소(%), 다음 고정값 감소. 물리/마법 각각 별도 수치.
- **최소 보장 데미지**: 방어 적용 전 값의 1/10 아래로는 내려가지 않는다 → 극단 방어 빌드 무력화 방지.
- 방어 관통 스킬 / 관통 수치가 별도로 존재.
- 1회 공격을 완전 무효화하는 배리어 개념 존재.
- 회복량도 같은 구조(`√지능 × 상수 + 장비 마공` × 배율).
- **데미지 난수가 주석 처리되어 꺼져 있다.** → 현재 원본의 전투는 완전 결정론적이다.

**[평가]**

- **제곱근 스케일링이 전 시스템에 일관되게 적용**되어 있다(속도, 공격력). 성장 인플레를 억제하는 좋은 축.
- 최소 보장 데미지 = 매우 중요한 안전장치. **채택.**
- 난수 제거는 의도적으로 보인다. 자동 전투 게임에서 난수는
  "내 규칙이 좋았나, 운이 좋았나"를 흐려서 학습 피드백을 망가뜨린다.
  → 우리도 **기본 결정론 + 난수는 명시적 스킬 효과로만** 도입하는 방향을 권장한다.

#### S6.5 시전과 경직

**[관찰]**

- 스킬은 선딜(준비/영창)과 후딜(경직)을 가진다.
- 선딜이 있는 스킬은 **예약 상태**로 들어가고, 다음 자기 차례에 실제로 발동한다.
- 예약 중인 캐릭터는 조건식에서 "시전 중"으로 관측 가능 → **끊기(interrupt) 전략**이 성립한다.
- 예약 시점에 타겟이 확정되므로, 발동 시점에 타겟이 이미 죽어 있을 수 있다.

**[평가]**

- 선딜을 "관측 가능한 상태"로 노출한 것이 이 시스템의 백미다. 규칙 언어와 전투 엔진이 맞물린다.

#### S6.6 종료 조건

**[관찰]**

- 한쪽 전멸 시 종료.
- 최대 행동 횟수 제한이 있고, 초과 시 무승부 처리.
- 단, **결착이 임박했다고 판단되면 정해진 만큼 연장**하고, 연장에도 상한이 있다.
- 상태이상(독)은 매 행동 시작 시 도트 데미지.
- 지속 회복 패시브도 매 행동 시작 시 적용.
- 일정 행동 횟수마다 전황(전원 HP/SP)을 로그에 요약 출력한다.
- 전투 로그는 일정 건수만 순환 보관한다.

**[평가]**

- "연장전" 아이디어는 좋다. 무한 힐 대치를 끊으면서도 아까운 접전은 살린다.
- 주기적 전황 요약은 긴 로그의 가독성을 살리는 저비용 장치. 채택.

### S7. 아이템 / 장비 / 강화 / 부여

**[관찰]**

- 장비 타입이 매우 세분화되어 있다:
  한손검 / 양손검 / 단검 / 양손창 / 한손창 / 양손도끼 / 한손도끼 / 지팡이(1H) / 지팡이(2H) / 둔기 / 활 / 석궁,
  방패 / 방어용 단검 / 책, 갑옷 / 의복 / 로브
- 직업별로 장착 가능 타입이 화이트리스트로 지정된다.
- 양손 무기는 방패와 배타적이다.
- 장비는 `(물리공격, 마법공격)` 과 `(물리 비율방어, 물리 고정방어, 마법 비율방어, 마법 고정방어)` 를 가진다.
- **아이템 인스턴스를 하나의 문자열 ID로 인코딩한다**:
  `[기본번호 4자리][강화수치 2자리][옵션1 3자리][옵션2 3자리][옵션3 3자리]`
  → 강화도 옵션도 없으면 앞 4자리만 저장(공간 절약).
- **강화(정련)**: 상한이 있고(관찰값 10), 낮은 단계는 100% 성공,
  이후 성공률이 계단식으로 급락한다(관찰값 60 → 40 → 40 → 20 → 20 → 10%).
  **실패해도 파괴되거나 수치가 내려가지 않는다.**
- **옵션 부여**: 제작 시 확률적으로 상급/하급 옵션 슬롯이 붙는다.
  관찰된 분포는 하급만 / 상급만 / 둘 다 가 각각 1/3.
- 옵션 종류: 공격력·방어력·최대HP·최대SP·각 스탯의 가산 또는 승산, 소환력 강화, 관통 등

**[평가]**

- 문자열 인코딩 ID는 DB 없이 파일로 굴리던 시절의 영리한 해법이지만, **우리에겐 안티패턴**이다.
  → 정규화된 아이템 인스턴스 테이블을 쓴다.
- **강화 실패 시 파괴/하락이 없다**는 점이 중요하다. 원본은 도박성을 의도적으로 낮췄다.
  상업화 시 이 결정은 유지할 가치가 크다(규제 및 유저 신뢰 양쪽).
- 장비 타입 세분화 + 직업 화이트리스트 = 빌드 정체성 형성. 좋다.

### S8. 제작 (대장간)

**[관찰]**

- 제작 가능 아이템 목록이 별도로 관리되고, 각 아이템은 필요 재료와 수량을 가진다.
- 재료는 몬스터 드롭으로 수급한다.
- 제작 결과물에 확률적으로 옵션이 부여된다(S7) → **같은 아이템도 뽑기 결과가 다르다.**
- 추가 재료를 넣으면 특정 부가 효과의 부여 확률에 개입할 수 있는 구조가 있다.

**[평가]**

- "제작 = 저확률 옵션 뽑기"는 경매장(S9)에 물건을 공급하는 엔진이다. 경제 설계의 핵심 축.
- 다만 **여기가 사실상의 뽑기**이므로, 상업화 시 이 지점에 유료 재화를 붙이지 않도록 주의해야 한다.

### S9. 경매장 / 경제

**[관찰]**

- 유저 간 아이템 거래소. 출품 · 입찰 · 낙찰 · 로그.
- 동시 출품 수 제한 존재(관찰값 100).
- 운영자가 **경매장 자체와 "출품 기능"을 각각 따로 끌 수 있다** → 초기 서버에서는 거래를 잠가둘 수 있다.
- 판매가가 별도 지정되지 않은 아이템은 구매가의 고정 비율로 자동 산정.
- 경험치·재화 획득 배율이 전역 설정으로 조절 가능하다(이벤트 운영용).

**[평가]**

- 거래 기능을 단계적으로 여는 스위치를 처음부터 둔 것은 운영 경험이 반영된 설계다. **채택.**
- 다만 아이템 싱크(소모처)가 약하다. 강화 실패에도 파괴가 없으므로 **인플레이션이 필연**이다.
  → 우리는 별도의 싱크를 반드시 설계해야 한다.

### S10. 콜로세움 — 비동기 PvP 랭킹

**[관찰]**

- 사다리(ladder) 방식. **자신보다 정확히 한 계단 위의 상대에게만 도전 가능.**
- 승리하면 순위를 맞바꾼다.
- 미등록자가 도전하면 최하위로 편입된 뒤 바로 위와 붙는다.
- **1위는 도전할 수 없다** (방어만 가능).
- 도전 쿨타임이 승패에 따라 비대칭이다: 패배 시 길고(관찰값 24시간), 승리 시 매우 짧다(관찰값 1분).
  → 연승 시 빠르게 치고 올라가고, 지면 강제 휴식. 좋은 페이싱.
- **랭킹 전용 파티 편성을 따로 저장**하며, 그 편성은 긴 주기로만 변경 가능하다(관찰값 48시간).
  → 상대는 내 "저장된 방어 편성"과 싸운다. 실시간 접속 불필요 = 진짜 비동기.
- 같은 순위에 복수 인원이 존재할 수 있는 구조(동순위 그룹).
- 1위와의 대결은 별도로 "방어전"으로 취급되어 처리가 다르다.

**[평가]**

- **"방어 편성을 자주 못 바꾼다"가 핵심 규칙이다.** 이게 없으면 카운터 편성 즉시 대응이 가능해져
  규칙 설계 게임이 아니라 가위바위보가 된다. 반드시 계승.
- "한 계단 위만 도전 가능" = 매치메이킹 로직이 필요 없다. 우아하다.
- 승/패 쿨타임 비대칭도 훌륭하다. 실력 있는 유저가 빠르게 제자리를 찾는다.
- 단점: 인구가 늘면 하위 유저가 상위까지 올라가는 데 걸리는 도전 횟수가 O(n)이다.
  → **구간(디비전) 도입**으로 완화해야 한다.

### S11. 유니온 — 협동 레이드

**[관찰]**

- 주기적으로 등장하는 특수 강화 몬스터(및 동반 잡몹). 여러 유저가 나눠서 때린다.
- **HP가 유저에게 공개되지 않는다** (전투 중 `????` 로 표시).
- **부활하지 않는다** — 일반 몬스터와 달리 죽으면 그 개체는 끝.
- 보상은 "가한 데미지 차분"에 비례해 경험치가 분배되는 방식.
- 소모 행동력이 일반 전투보다 훨씬 적고(관찰값 10 vs 100), 별도의 짧은 쿨타임이 있다(관찰값 20분).
- 레벨 제한, 출현 주기, 동반 잡몹 구성/수량, 배경 등이 데이터로 지정된다.
- 독 저항 등 레이드 전용 특수 능력을 부여할 수 있다.

**[평가]**

- **HP 비공개가 영리하다.** "얼마나 남았는지 모르니 계속 때린다" = 참여 유도 + 막타 독식 방지.
- 낮은 행동력 비용 = "본 게임과 별개로 매일 가볍게 참여하는 콘텐츠". 리텐션 장치로 정확하다.
- 데미지 기여 비례 보상은 공정하지만 **딜러만 보상받는 구조**다. 힐/탱 기여 보정이 필요하다.

### S12. 진행과 해금

**[관찰]**

- **지역 해금**: 기본 지역 몇 곳은 무조건 개방. 나머지는 **특정 아이템(통행증 성격)을 보유**해야 개방된다.
- 지역마다 등장 몬스터와 **가중치**가 지정되고, 가중치 합으로 나눠 확률을 낸다.
  → 합을 100으로 맞출 필요가 없어 밸런싱이 편하다.
- 몬스터에 "숨김" 플래그가 있어 **목록에 표시되지 않는 희귀 조우**를 만들 수 있다.
- **시간대 한정 지역**이 존재한다 (특정 시각의 특정 분 구간에만 등장하는 히든 지역).
- 마을 시설(상점 / 모집 / 대장간 / 경매장 / 콜로세움)도 동일한 조건부 해금 구조를 갖는다.
  현재는 전부 무조건 개방이지만 확장 지점이 열려 있다.
- 몬스터 드롭은 만분율 확률 테이블이며, **한 번에 최대 1개만 드롭**된다.
- 지역에는 권장 레벨 표기와 배경 이미지 키가 붙는다.

**[평가]**

- "가중치 합을 정규화하지 않음"과 "만분율 드롭"은 실무적으로 훌륭한 선택. 그대로 채택.
- **숨김 몬스터 + 시간대 한정 지역**은 커뮤니티에 발견의 재미를 주는 저비용 장치다. 아주 좋다.
- 아이템 기반 지역 해금은 단순하지만 확장성이 좋다(퀘스트 시스템 없이도 진행 게이트를 만들 수 있다).

## 3. 우리 게임의 설계 방향 (초안)

> 아래는 원본을 그대로 따르지 않는, **우리의 결정**이다.

### 3.1 계승할 아이디어 (원본의 강점)

1. 규칙 프로그래밍이 게임플레이의 중심
2. `(진영, 범위, 횟수)` 대상 지정 3튜플
3. 선딜을 관측 가능 상태로 노출 → 카운터 플레이 성립
4. 제곱근 기반 수확 체감 (속도 · 공격력)
5. 최소 보장 데미지 / 버프 상한
6. 전열 커버 + 캐릭터별 방어 성향
7. 타겟 우선순위의 선호형 / 한정형 구분
8. 사다리형 비동기 PvP + 방어 편성 변경 제한 + 승패 비대칭 쿨타임
9. 레이드 HP 비공개 + 낮은 행동력 비용
10. 가중치 조우 테이블 / 만분율 드롭 / 숨김 몬스터 / 시간 한정 콘텐츠
11. 강화 실패 시 파괴 없음
12. 거래 기능 단계적 개방 스위치

### 3.2 반드시 개선할 것 (원본의 약점)

| # | 원본의 문제 | 우리의 해법 |
|---|---|---|
| 1 | 규칙 조건이 AND만 지원 | **OR / NOT / 괄호를 지원하는 조건 표현식**. 단 UI는 블록 에디터로 감싸 복잡도를 숨긴다 |
| 2 | 패턴 저장·공유·복제 불가 | **패턴 프리셋 시스템** + 유저 간 패턴 공유(코드 문자열 또는 갤러리). 강력한 바이럴 장치가 된다 |
| 3 | 검증하려면 실제 전투(행동력 소모) 필요 | **행동력 0의 샌드박스 시뮬레이터**. 임의 상대를 세워두고 N회 자동 대전 → 승률과 실패 원인 리포트 |
| 4 | 복잡한 스킬이 코드에 하드코딩 | **이펙트 DSL** — 스킬 = 조건부 이펙트의 배열. 신규 스킬을 코드 수정 없이 데이터로 추가 |
| 5 | 전투 로그가 단순 텍스트 나열 | **타임라인 뷰어** — 각 행동에 "왜 이 스킬이 선택되었는가(발동한 규칙 번호)"를 표시. 이게 핵심 UX |
| 6 | 부동소수점 → 재현성 불안 | **정수 고정소수점 + 시드 고정** = 완전 결정론. 리플레이는 시드 + 편성만으로 재생 |
| 7 | 아이템을 문자열 ID로 인코딩 | 정규화된 인스턴스 테이블 |
| 8 | 경제에 싱크가 없음 | 강화 재료 소모, 콜로세움 참가비, 패턴 슬롯 확장 등 **재화·아이템 소각처**를 명시적으로 설계 |
| 9 | 사다리가 O(n) | **디비전 분할 + 시즌제** |
| 10 | 레이드가 딜 기여만 보상 | 가한 피해 + 받은 피해 + 회복량을 합산한 **기여도 점수** |
| 11 | 2단 직업 트리로 얕음 | 3단 또는 **서브클래스 조합**으로 빌드 공간 확대 (추후 결정) |
| 12 | 튜토리얼이 정적 텍스트 | 규칙 에디터를 가르치는 **인터랙티브 퍼즐 스테이지** (정해진 적을 정해진 규칙 수 안에 이기기) |

### 3.3 상업화 설계 원칙 (초안)

- **행동력을 직접 파는 구조는 지양.**
  이 게임의 실력은 규칙 설계이므로, 시행 횟수를 돈으로 사면 코어가 붕괴한다.
- 판매 대상 후보: 캐릭터 슬롯, 패턴 프리셋 슬롯, 시뮬레이터 동시 실행 수, 코스메틱, 시즌 패스
- **강화 확률 뽑기 판매는 하지 않는다** (규제 리스크 + 이 게임의 정체성과 불일치)
- 결정론적 전투이므로 "확률 조작" 의심이 원천 차단된다 — 이걸 신뢰 마케팅 포인트로 삼을 수 있다

### 3.4 기술 스택 제안

- **전투 엔진을 순수 함수 패키지로 완전 분리**
  (입력: 편성 + 규칙 + 시드 → 출력: 이벤트 로그. 부수효과 없음)
  → 서버 · 클라이언트 · 시뮬레이터 · 밸런싱 배치가 전부 같은 엔진을 공유한다
- TypeScript — 엔진을 서버와 브라우저 양쪽에서 그대로 실행할 수 있다
- 서버: Node + 관계형 DB (파일 기반 저장은 원본의 명백한 한계였다)
- 클라이언트: 웹. 규칙 에디터가 UI의 90%이므로 폼/드래그 UX가 성패를 가른다
- 리플레이 = 이벤트 로그 스트림. 저장 비용이 낮고 서버 검증도 가능하다

## 4. 다음 단계 (미결정 사항)

작업을 진행하려면 다음이 정해져야 한다.

1. **세계관 / 톤** — 정통 판타지? 다른 소재(SF, 무협, 현대)? → 명칭과 아트 방향이 여기서 갈린다
2. **직업 트리 깊이** — 2단 유지 vs 3단 vs 서브클래스 조합
3. **PvP 비중** — 콜로세움이 엔드게임의 전부인가, PvE 레이드가 축인가
4. **플랫폼** — 웹 전용 / 모바일 웹 대응 / 앱
5. **첫 마일스톤 범위** — 권장안:
   > **M1 = 전투 엔진 + 규칙 에디터 + 시뮬레이터.**
   > 계정 · 경제 · PvP는 전부 제외하고, 로컬에서 "규칙을 짜서 봇과 싸운다"까지만 만든다.
   > 이 게임의 재미가 성립하는지 여부는 M1에서 100% 판명된다.
