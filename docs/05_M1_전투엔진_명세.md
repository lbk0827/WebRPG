## 1. M1의 목적

M1은 게임을 만드는 단계가 아니라 **하나의 질문에 답하는 단계**다.

> **"교전 수칙을 짜는 것 자체가 재미있는가?"**

여기서 답이 안 나오면 육성도 경제도 PvP도 의미가 없다.
따라서 M1은 그 질문에 필요한 최소한만 만들고, 나머지는 전부 뺀다.

### 검증 항목

| # | 질문 | 판정 방법 |
|---|---|---|
| V1 | 수칙을 고쳐서 이기게 되는 경험이 재미있는가 | 훈련 과제 플레이 테스트 |
| V2 | 전황 보고서를 읽고 실패 원인을 스스로 찾을 수 있는가 | 테스터가 힌트 없이 원인을 말할 수 있는지 |
| V3 | **모바일 폭에서 수칙 편집이 쓸 만한가** | ADR-001의 최대 리스크 항목 |
| V4 | 조건 타입이 충분한가 / 과한가 | 테스터가 "이런 조건이 없다"고 말하는 빈도 |

## 2. 범위

### 포함

- 전투 엔진 (5 vs 5, 결정론)
- 수칙 편집기 (조건식 + 스킬 지정 + 행 순서)
- 전황 보고서 뷰어 (발동 조항 표시)
- 훈련장 (행동력 개념 없음, N회 반복 대전 + 승률 리포트)
- 고정 프리셋 단원 6~8종
- 훈련 과제 12~15개

### 제외 — M2 이후

레벨업 · 경험치 · 스탯 분배 · 직업/전직/스킬트리 · 장비 · 제작 · 강화 · 경제/거래소 ·
행동력 · 계정/서버 · 투기장 · 토벌 의뢰 · 소환수 · 마법진 · 넉백/강제이동 · 지역/드롭

> M1의 단원은 **스탯도 보유 스킬도 고정**이다. 플레이어가 바꾸는 것은 **수칙과 편성뿐**이다.
> 변수를 하나로 줄여야 V1의 답이 명확해진다.

## 3. 엔진 인터페이스

전투 엔진은 **부수효과 없는 순수 함수 패키지**다. DOM·네트워크·시간·전역 상태에 접근하지 않는다.

```ts
function simulate(input: BattleInput): BattleResult

interface BattleInput {
  seed: number                  // 이 값이 같으면 결과가 완전히 같다
  teams: [TeamSetup, TeamSetup]
  config: BattleConfig
}

interface BattleResult {
  outcome: 'team0' | 'team1' | 'draw'
  actionCount: number
  events: BattleEvent[]         // 이것이 전황 보고서의 원본
}

interface BattleConfig {
  maxActions: number            // 초과 시 무승부
  extendActions: number         // 결착 임박 시 연장 폭
  maxExtends: number
  statusReportInterval: number  // N회 행동마다 전황 요약 이벤트 삽입
}
```

### 3.1 결정론 요구사항 (필수)

ADR-001에서 결정한 대로 **완전 결정론**을 보장한다. 위반 시 비동기 PvP가 성립하지 않는다.

1. **부동소수점 금지.** 모든 내부 수치는 정수. 소수가 필요한 곳은 **고정소수점(스케일 1000)** 을 쓴다
2. **난수는 시드 기반 PRNG 하나만 사용.** `Math.random()` 호출 금지 (린트 규칙으로 강제)
3. **순회 순서 고정.** 객체 키 순회 금지, 항상 배열 인덱스 순서
4. **셔플은 시드 기반 Fisher-Yates**
5. 같은 `BattleInput`으로 두 번 실행하면 `events` 배열이 바이트 단위로 동일해야 한다
   → **이걸 테스트로 강제한다** (골든 테스트)

## 4. 전투 규칙

### 4.1 행동 순서 — 게이지

- 각 단원은 0에서 1000까지 차오르는 게이지를 가진다 (고정소수점)
- 충전 속도 = `floor(sqrt(SPD) * K + BASE)` — **제곱근이므로 속도 투자에 수확 체감**
- 매 스텝마다 "가장 먼저 도달할 단원"을 계산해 그 시점까지 전원의 게이지를 일괄 진행 (이벤트 점프)
- 동시 도달 시 시드 기반 무작위 선택
- 사망 시 게이지 진행 정지

### 4.2 진형과 엄호

- 각 단원은 **전열 / 후열** 중 하나
- 후열이 대상이 되면, 살아있는 전열 아군이 대신 맞을 수 있다
- 엄호 여부는 단원별 **엄호 방침**으로 결정
- 후보는 시드 셔플 후 앞에서부터 판정 (특정 인원에게 몰리지 않도록)
- HP가 1 이하인 전열은 엄호 불가
- `ignoreCover` 스킬과 `isSupport` 스킬은 엄호 판정을 건너뛴다
- **엄호는 `scope: 'single'` 공격에만 적용된다.** 광역(`all`)·다중(`multi`) 공격은 전열이 막아줄 수 없다
  → 광역기가 방벽 편성의 자연스러운 카운터가 되도록 하는 설계 결정 (구현 중 확정)

```ts
type GuardPolicy =
  | { mode: 'always' }
  | { mode: 'never' }
  | { mode: 'hpAbove'; pct: number }   // 자기 HP가 pct% 초과일 때만
  | { mode: 'chance'; pct: number }    // pct% 확률로
```

### 4.3 데미지

```
기본치  = floor(sqrt(주스탯) * K) + 부가공격력
위력적용 = 기본치 * power / 100
최소보장 = 위력적용 / 10
방어적용 = 위력적용 * (1 - 비율방어/100) - 고정방어
최종     = max(방어적용, 최소보장)
```

- 물리는 STR, 마법은 INT 참조
- `pierce` 스킬은 방어 적용 단계를 건너뛴다
- **최소 보장 데미지**는 극단 방어 빌드 무력화를 막는 안전장치다. 반드시 유지한다
- **M1에서 데미지 난수는 넣지 않는다.** 자동 전투에서 난수는
  "내 수칙이 좋았나 운이 좋았나"를 흐려 학습 피드백을 망가뜨린다

### 4.4 시전과 경직

- 스킬은 `charge`(선딜)와 `stiff`(후딜)를 가진다
- `charge > 0` 인 스킬은 **예약 상태**로 들어가고, 다음 자기 차례에 발동한다
- 예약 중인 단원은 조건식에서 **"시전 중"으로 관측 가능** → **끊기 전략이 성립한다**
- 예약 시점에 대상이 확정되므로, 발동 시점에 대상이 이미 죽어 있을 수 있다 (의도된 동작)

> 이것이 이 게임의 시그니처 메커니즘이다. M1에서 절대 빼지 않는다.
> 이게 없으면 "적을 관측하는 조건"이 전부 무의미해진다.

### 4.5 수칙 평가

```ts
interface RuleSet { rows: RuleRow[] }

interface RuleRow {
  condition: Condition
  skillId: SkillId
  maxUses?: number     // "N회만" — 전투당 발동 횟수 상한
}
```

1. 자기 차례가 오면 `rows`를 **위에서부터 순서대로** 평가한다
2. **처음으로 참이 되는 행**의 스킬을 사용한다
3. `maxUses`에 도달한 행은 건너뛴다 (조건 평가 자체를 하지 않음)
4. 조건은 참인데 스킬을 쓸 수 없는 경우 — SP 부족 / 침묵 / 한정형 대상 없음 — 는
   `skillFailed`(사유 포함)를 남기고 **다음 행으로 넘어간다**.
   조건이 거짓인 행은 이벤트 없이 조용히 건너뛴다 (로그 소음 방지)
5. 모든 행이 거짓이거나 실패하면 **아무것도 하지 않고 차례를 넘긴다** → `ruleExhausted` 이벤트

> 6번이 핵심 학습 장치다. 세계관상 **"수칙에 없는 상황이라 단원이 우물쭈물했다"** 로 표시된다
> ([ADR-002](03_세계관_톤.md) 4.2 참조).
> 이 이벤트를 보고서에서 **눈에 띄게** 표시해야 한다. 이게 플레이어를 수칙 편집으로 돌려보낸다.

## 5. 조건 타입 (M1)

### 5.1 조건식 구조

원본은 AND만 지원했다. 우리는 **처음부터 표현식 트리**로 간다.
나중에 붙이면 훨씬 비싸다.

```ts
type Condition =
  | { op: 'always' }
  | { op: 'atom';  atom: ConditionAtom }
  | { op: 'and';   nodes: Condition[] }
  | { op: 'or';    nodes: Condition[] }
  | { op: 'not';   node: Condition }
```

- 중첩 깊이 상한 3 (UI 복잡도 관리)
- UI는 블록 에디터로 감싸 트리 구조를 숨긴다. 플레이어에게 "표현식"이라는 단어를 노출하지 않는다

### 5.2 원자 조건 목록

`side` 파라미터(`'ally' | 'enemy'`)로 아군/적군 버전을 통합했다.
원본의 약 30종 조건을 **16종**으로 압축했으면서 표현력은 더 넓다.

```ts
type Cmp  = 'gte' | 'lte' | 'eq'
type Side = 'ally' | 'enemy'
type Row  = 'front' | 'back'
```

| # | kind | 파라미터 | 의미 |
|---|---|---|---|
| 1 | `selfHpPct` | cmp, value | 자신 HP 비율 |
| 2 | `selfHpAbs` | cmp, value | 자신 HP 절대값 |
| 3 | `selfSpPct` | cmp, value | 자신 SP 비율 |
| 4 | `selfSpAbs` | cmp, value | 자신 SP 절대값 — 고비용 스킬 게이팅용 |
| 5 | `selfRow` | row | 자신이 전열/후열인가 |
| 6 | `selfHasStatus` | status | 자신이 특정 상태인가 |
| 7 | `selfActionCount` | cmp, value | 자신의 누적 행동 횟수 (`eq`로 "N회째" 표현) |
| 8 | `teamAliveCount` | side, cmp, value | 생존자 수 |
| 9 | `teamDeadCount` | side, cmp, value | 전사자 수 |
| 10 | `teamAnyHpPctBelow` | side, value | HP가 N% 이하인 대상이 존재 |
| 11 | `teamAvgHpPct` | side, cmp, value | 평균 HP 비율 — 전황 판단용 |
| 12 | `teamCastingCount` | side, cmp, value | **시전 중인 인원 수** ★ 끊기 조건 |
| 13 | `teamStatusCount` | side, status, cmp, value | 특정 상태인 인원 수 |
| 14 | `teamRowCount` | side, row, cmp, value | 전열/후열 인원 수 |
| 15 | `teamSpPctBelow` | side, value | SP가 N% 이하인 대상이 존재 |
| 16 | `chance` | percent | N% 확률 — 상대가 내 수칙을 완전히 읽지 못하게 하는 노이즈 |

**설계 의도**

- **1·2번(비율/절대값 병존)은 의도적이다.** "HP 200 이하"와 "HP 30% 이하"는 완전히 다른 전술이다
- **10번**은 적에게 쓰면 마무리 타격 조건(`enemy`, 30), 아군에게 쓰면 힐 조건(`ally`, 40)이 된다
- **12번**이 4.4의 시전 시스템과 맞물려 카운터 플레이를 만든다. 이 조건이 없으면 선딜이 무의미하다
- **"N회만"은 조건이 아니라 `RuleRow.maxUses`로 뺐다.** 조건식에 넣으면 상태 추적이 지저분해진다

### 5.3 M1에서 제외한 조건

소환수 수 · 마법진 수 · 개별 능력치(STR/INT/DEF 등) 비교 · 적 레벨 조건

> 능력치 비교 조건은 M1에서 스탯이 고정이므로 쓸모가 없다. M2에서 부활시킨다.

## 6. 스킬

### 6.1 스킬 스키마

```ts
interface Skill {
  id: SkillId
  spCost: number
  target: TargetSpec
  priority?: TargetPriority
  charge: number          // 선딜 (0 = 즉시)
  stiff: number           // 후딜
  ignoreCover?: boolean   // 엄호 무시
  isSupport?: boolean     // 아군 대상 → 엄호 판정 제외
  effects: Effect[]
}

interface TargetSpec {
  side:  'ally' | 'enemy' | 'any' | 'self'
  scope: 'single' | 'multi' | 'all'
  hits:  number
}
```

`TargetSpec`은 원본의 가장 우아한 추상화를 계승한 것이다.

| 예시 | 의미 |
|---|---|
| `{enemy, single, 3}` | 적 1명을 3회 타격 |
| `{enemy, multi, 4}` | 적 중 4명을 무작위로 1회씩 (중복 선택 가능) |
| `{enemy, all, 2}` | 적 전원을 2회씩 |
| `{ally, single, 1}` | 아군 1명에게 1회 |

### 6.2 타겟 우선순위 — 선호형 / 한정형

```ts
type TargetPriority =
  | { mode: 'prefer';  by: 'lowestHpPct' | 'highestHpPct' | 'backRow' }
  | { mode: 'require'; by: 'dead' | 'casting' | 'debuffed' }
  | { mode: 'require'; by: 'hasStatus'; status: StatusId }
```

> `debuffed`는 정화 스킬용으로 구현 중 추가했다. "디버프가 하나라도 있는 아군"을 한정형으로 고른다.

- **`prefer`** — 해당 대상이 없으면 아무나 고른다. 스킬은 반드시 발동한다
- **`require`** — 해당 대상이 없으면 **스킬 사용이 실패**하고 다음 수칙 행으로 넘어간다

> 부활기를 전사자가 없을 때 헛되이 쓰지 않게 하는 장치다. 이 구분은 반드시 유지한다.

### 6.3 효과 프리미티브

원본은 복잡한 스킬을 코드에 하드코딩했다. 우리는 **효과를 데이터로 조합**한다.
신규 스킬 추가에 코드 수정이 필요 없어야 한다.

```ts
type Effect =
  | { kind: 'damage';       school: 'phys' | 'magic'; power: number; pierce?: boolean }
  | { kind: 'heal';         power: number }
  | { kind: 'restoreSp';    power: number }
  | { kind: 'applyStatus';  status: StatusId; duration: number; magnitude?: number }
  | { kind: 'removeStatus'; category: 'debuff' | 'buff' }
  | { kind: 'modifyGauge';  delta: number }        // + 가속 / − 지연
  | { kind: 'revive';       hpPct: number }
  | { kind: 'shield';       hits: number }
```

- `effects` 배열은 순서대로 적용된다 (예: 데미지 → 디버프 부여)
- 프리미티브 8종만으로 M1의 모든 스킬을 표현할 수 있어야 한다.
  표현 불가능한 스킬이 나오면 **하드코딩하지 말고 프리미티브를 추가한다**

### 6.4 상태이상 (M1)

| id | 분류 | 효과 |
|---|---|---|
| `poison` | 디버프 | 자기 차례 시작 시 지속 피해 |
| `atkUp` / `atkDown` | 버프 / 디버프 | 공격력 증감 |
| `defUp` / `defDown` | 버프 / 디버프 | 방어력 증감 |
| `spdUp` / `spdDown` | 버프 / 디버프 | 게이지 충전 속도 증감 |
| `silence` | 디버프 | SP 소모 스킬 사용 불가 → 기본 공격만 가능 |
| `barrier` | 버프 | 공격 N회 완전 무효 |

- 스탯 증감에는 **상한**을 둔다 (초기값 대비 배수 캡). 버프 중첩으로 인한 수치 폭주 차단
- `silence`는 수칙 설계에 좋은 압력을 준다 — "침묵당하면 무엇을 할 것인가"를 미리 정해야 한다

### 6.5 M1 스킬 세트 (약 15종)

명칭은 미정([ADR-002](03_세계관_톤.md) 6장). **역할 원형만 확정한다.**

| 원형 | 구성 |
|---|---|
| 기본 공격 | SP 0, 물리 단일 1타, 선딜 0 — 모든 단원이 보유 |
| 강타 | 물리 단일 고위력, 선딜 있음 |
| 연타 | 물리 단일 3타 저위력 |
| 광역 물리 | 적 전원 1타 |
| 기본 마법 | 마법 단일 |
| 광역 마법 | 적 다수 4명, 선딜 김 — **끊기의 표적** |
| 관통 마법 | `ignoreCover`, `prefer: backRow` |
| 단일 회복 | `ally single`, `prefer: lowestHpPct` |
| 광역 회복 | `ally all`, 선딜 있음 |
| 소생 | `require: dead` |
| 공격 강화 | `applyStatus: atkUp` |
| 방어 약화 | `applyStatus: defDown` |
| 지연 | `modifyGauge` 음수, `require: casting` — 끊기 **(지연형)**: 시전은 유지되고 발동만 늦어짐 |
| 침묵 | `applyStatus: silence`, `require: casting` — 끊기 **(취소형)**: 진행 중인 시전을 `castInterrupted`로 취소 |
| 보호막 | `shield` |
| 정화 | `removeStatus: debuff` |
| 기력 회복 | `restoreSp` |

**설계 의도**: 광역 마법(선딜 김)과 지연/침묵(`require: casting`)이 짝을 이룬다.
이 한 쌍이 "적을 관측하는 수칙"의 가치를 증명한다. **M1의 훈련 과제는 이 관계를 가르치는 데 초점을 둔다.**

## 7. 이벤트 로그

전황 보고서 뷰어의 원본 데이터. **UI가 요구하는 모든 정보가 여기 있어야 한다.**

```ts
type BattleEvent =
  | { t: 'battleStart';  teams: TeamSnapshot[] }
  | { t: 'turnBegin';    actor: CharRef }
  | { t: 'ruleFired';    actor: CharRef; ruleIndex: number; skillId: SkillId }  // ★
  | { t: 'ruleExhausted'; actor: CharRef }                                      // ★
  | { t: 'skillFailed';  actor: CharRef; skillId: SkillId
                       ; reason: 'noSp' | 'noRequiredTarget' | 'silenced' }     // ★
  | { t: 'castStart';    actor: CharRef; skillId: SkillId }
  | { t: 'castResolve';  actor: CharRef; skillId: SkillId }
  | { t: 'castInterrupted'; target: CharRef; skillId: SkillId }   // 침묵으로 시전 취소
  | { t: 'cover';        defender: CharRef; protectedChar: CharRef }
  | { t: 'damage';       source: CharRef; target: CharRef; amount: number
                       ; school: 'phys' | 'magic'; nullified?: boolean }
  | { t: 'heal';         source: CharRef; target: CharRef; amount: number }
  | { t: 'spChange';     target: CharRef; delta: number }
  | { t: 'statusApply';  target: CharRef; status: StatusId; duration: number }
  | { t: 'statusTick';   target: CharRef; status: StatusId; amount: number }
  | { t: 'statusExpire'; target: CharRef; status: StatusId }
  | { t: 'gaugeShift';   target: CharRef; delta: number }
  | { t: 'death';        target: CharRef }
  | { t: 'revive';       target: CharRef; hp: number }
  | { t: 'statusReport'; snapshot: TeamSnapshot[] }
  | { t: 'battleEnd';    outcome: Outcome; actionCount: number }
```

**★ 표시 3종이 이 게임의 UX 핵심이다.**

- `ruleFired.ruleIndex` → 보고서에 **"3번 조항 발동"** 으로 표시.
  플레이어가 "왜 이 스킬이 나왔지"를 즉시 추적할 수 있어야 한다
- `ruleExhausted` → **"수칙에 없는 상황이라 우물쭈물했다"**. 눈에 띄게 강조
- `skillFailed.reason` → **"SP 부족" / "대상 없음" / "침묵 상태"**. 디버깅의 결정적 단서

> 원본에는 이 세 가지가 전부 없었다. 플레이어는 결과만 보고 원인을 추측해야 했다.
> **이것이 우리의 가장 큰 차별점이다.**

**구현 제약**: 보고서 뷰어는 **이벤트 재생기(커서 · 속도 · 건너뛰기)** 와 **렌더러(타임라인)** 를 분리해서 만든다.
M2 의 시각적 전투 스테이지는 같은 재생기 위에 렌더러만 추가한다 ([06_리소스_목록.md](06_리소스_목록.md) §4).

## 8. M1 콘텐츠

### 8.1 프리셋 단원 6~8종
스탯과 보유 스킬 고정. 역할 원형: 전열 방벽 / 전열 딜러 / 후열 물리 / 후열 마법 / 회복 / 방해(끊기).
플레이어는 이 중 5명을 골라 편성하고 수칙만 짠다.

### 8.2 훈련 과제 12~15개
정해진 상황과 목표를 주고, 수칙을 고쳐서 달성하게 하는 한 판. 인터랙티브 튜토리얼이자 첫 게임 콘텐츠다.

**검증 원칙 (2026-09-10 확정)**: 과제는 사람이 플레이하기 전에 테스트로 검증한다.
`test/missions.test.ts` 가 각 과제에 대해 다음을 강제한다.
- 기본 수칙으로는 완료하지 못한다 (고정 시드 + 시드 10개 중 7 이상 실패)
- 정답(`solution`)으로는 완료한다 (고정 시드 + 시드 10개 중 7 이상 완료)
→ 이 테스트를 통과한 과제만 플레이어에게 나간다. 튜닝 과정에서 "기본으로도 이김", "정답도 짐",
"아무도 안 죽어 소생할 대상이 없음" 같은 결함이 전부 사람 플레이 전에 잡혔다.

과제 스키마: 편집 가능 슬롯(`editable`), 제한(`limits`: 순서만 / 엄호만 / 조항 수), 추가 목표(`objective`: 생존·소생),
훈련용 상대의 스탯 덮어쓰기(`stats`). 실패 시 `analyze()` 기반 원인 한 줄 + 힌트.

**현재 7개 완성** (1 순서 · 2 fallback · 3 임계값 · 4 엄호 · 5 끊기★ · 6 오프너 · 7 소생). 나머지는 플레이 테스트 후 설계.

진행 곡선:
1. 순서 개념 — 조건 순서만 바꿔서 이기기
2. 자원 관리 — SP 고갈을 막는 fallback 조항 작성
3. 회복 타이밍 — `teamAnyHpPctBelow` 임계값 조정
4. 진형/엄호 — 엄호 방침 설정
5. **끊기** — 적의 광역 마법을 시전 중에 차단 ★ 클라이맥스
6. 복합 조건 — AND/OR가 필요한 상황
7. 확률 노이즈 — 결정적 수칙의 취약점 체험

스테이지마다 **"조항 3개 이내로 클리어"** 같은 제약을 걸면 최적화 재미가 붙는다.

### 8.3 훈련장
임의 편성 vs 임의 편성을 N회(예: 100회) 반복 실행하고 승률·평균 턴·사망 순서를 리포트한다.
행동력 개념이 없으므로 무제한이다. **원본에 없던 기능이며, M1의 핵심 도구다.**

## 10. 미결정 / 튜닝 기록

**2026-09-09 엔진 코어 완성 시점의 훈련장 관찰**

- `maxActions` 100 → **300** 으로 상향. 10명 전투에서 100은 인당 10회에 불과해
  교란자 미러전(상호 침묵 교착)이 전부 무승부로 잘렸다. 300에서는 무승부 0.
- 프리셋 팀 대진표(각 100회): 미러전은 전부 46~57%로 정상.
  **control(교란자 포함)이 79/73/68%로 가장 강함** — 끊기 메커니즘이 시그니처답게 강력하다는 증거이나,
  balanced 상대 79%는 과하다. 침묵 지속시간(2턴) 또는 `hush` SP 비용(12)이 1차 튜닝 후보.
- `rush`(힐러 없음)는 balanced 에 3%. 지속력 없는 편성이 지는 건 의도된 결과.

**2026-09-10 직업 5종으로 프리셋 정리 후 (assets/manifest.json 과 1:1)**

- 대진표가 크게 바뀜: `rush`(전사×2, 도적, 엘프×2)가 99 / 100 / 91%.
  원인은 구조적 — 엘프 2명의 관통 사격(엄호 무시 + 후열 우선)이 마법사·프리스트를 5턴 안에 지우고,
  도적의 침묵이 유일한 광역 딜(대화염)을 막는다. 상대 팀의 **기본 수칙이 이를 대응하지 않기 때문**이지
  스킬 수치 문제가 아니다. (전사에 "적 후열 ≥ 2 → 휩쓸기", 프리스트에 "보호막 우선" 같은 조항이 없다)
- → 이건 곧 **훈련 과제 소재**다: "엘프 저격수가 후열을 지운다. 수칙으로 막아라."
  수치 튜닝은 사람이 수칙을 직접 짜본 뒤에 한다.
