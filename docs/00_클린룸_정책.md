# 클린룸 정책 (Clean-room Policy)

이 프로젝트가 지켜야 할 저작권 규율. **작업 시작 전 반드시 읽을 것.**

---

## 1. 배경

일본 웹게임 `Hall of Fame`(원저작자: Juice / Tekito, 2007-2008)의 소스가
GitHub에 공개되어 있으나, 동봉된 이용규정은 다음과 같다.

- 저작권은 원저작자가 보유한다
- 설치 시 표시되는 저작권 표기를 삭제할 수 없다
- 개조·재배포는 자유
- 개조 시 원본과 구분되도록 저작권부에 추가 기재해야 한다
- **이 스크립트로 직접 수익을 내는 상업적 이용은 금지한다** (개인 배너 광고는 허용)
- 원저작자가 불이익하다고 판단하면 일방적으로 사용 중단을 요구할 수 있다
- 이 규약은 예고 없이 변경될 수 있다

즉 오픈소스 라이선스(MIT/GPL 등)가 아니라 **비상업 한정 무료 배포 스크립트**다.
`LICENSE` 파일은 존재하지 않으며, 조건이 언제든 바뀔 수 있고 사용 중단 요구도 가능하므로
**사업의 기반으로 삼을 수 없다.**

### 추가 리스크

- 한국의 게임114가 일본 외 지역 권리를 취득했다가 2017년 폐업했다는 이야기가 있으나,
  **회사가 폐업해도 저작권은 소멸하지 않는다.** 청산 과정에서 자산으로 남거나 제3자에게 이전된다.
  "권리자 행방불명"과 "권리 없음"은 다르다.
- 어느 쪽이든 원저작자 Juice / Tekito의 원저작권은 그대로 살아있다.
- 현재 국내 사설 서버들이 운영 중인 것은 "합법이라 괜찮은 것"이 아니라
  **권리자가 단속하지 않는 상태**에 가깝다. 수익 규모가 커지면 상황이 달라진다.
- 원본에 포함된 이미지·아이콘은 대부분 **제3자 배포 소재**이며 각자의 규약(대부분 비상업 한정)을 따른다.

## 2. 우리의 원칙

저작권은 **표현(expression)** 을 보호하고 **아이디어(idea)** 는 보호하지 않는다.
게임의 규칙·시스템·메커니즘은 원칙적으로 저작권 보호 대상이 아니다.

### ✅ 참고해도 되는 것 — 아이디어 영역

- 게임 루프, 진행 구조, 시스템 개념
- 메커니즘의 작동 원리 (예: "게이지가 차면 행동한다", "조건 목록을 위에서부터 평가한다")
- 수학적 구조 (예: "속도의 제곱근에 비례해 충전한다", "방어는 비율 감소 후 고정 감소")
- 설계 판단의 이유 (예: "방어 편성을 자주 못 바꾸게 해야 게임이 성립한다")
- **화면 구성과 정보 구조** — 어떤 구역이 어떤 순서로 있고, 무엇을 한 화면에 모으고,
  어떤 정보를 어느 단계에서 보여 주는가 (2026-09-12 단장 확인으로 명문화)

  UI 의 **배치와 정보 설계는 아이디어**다. "전투 화면에서 편성을 바꿀 수 있게 한다",
  "지역마다 접이식으로 두고 안에 등장 상대를 넣는다", "전투 로그에 HP 전/후를 같이 적는다" —
  전부 여기 해당한다. 공개된 화면을 보고 관찰해 **우리 코드로 다시 만드는 것**은 문제없다.
  실제 관찰과 판단은 [11_제로식_UI_분석_및_UI_개선.md](11_제로식_UI_분석_및_UI_개선.md) 에 전부 기록한다.

  **다만 그 화면의 CSS · 마크업 · 문구 · 이미지를 옮기는 것은 아래 ❌ 그대로다.**
  우리가 가져오는 것은 "무엇을 어디에 두는가"이지 "그것이 어떻게 생겼는가"가 아니다.

### ❌ 절대 가져오면 안 되는 것 — 표현 영역

- **소스 코드** — 한 줄도, 변형해서도, 다른 언어로 번역해서도 안 됨
- **변수명 · 함수명 · 클래스명 · 파일 구조**를 그대로 따라가는 것
- **데이터 테이블 전체** (아이템/몬스터/스킬/직업의 수치 세트 통째로)
  → 개별 숫자는 아이디어에 가깝지만, 선택·배열·구성의 편집물은 보호될 소지가 있다
- **고유명사** — 스킬명, 아이템명, 몬스터명, 직업명, 지역명
- **텍스트** — 튜토리얼, 매뉴얼, 아이템 설명, 전투 메시지
- **이미지 · 아이콘 · 사운드 · CSS 디자인**
- **`Hall of Fame` / `HOF` 라는 명칭** — 국내 인지도가 있으므로 상표·부정경쟁 리스크

## 3. 실무 규칙

1. **원본 소스는 이 저장소 바깥에 둔다.**
   위치: `../_Reference_ReadOnly/Hall-of-Fame/`
   이 프로젝트 폴더 안으로 절대 들여오지 않는다.
   git 히스토리에 원본 파일이 한 번이라도 들어가면 그 자체가 재배포이자 오염 근거가 된다.

2. **관찰 → 명세 → 구현의 순서를 지킨다.**
   원본은 문서와 실행 결과를 관찰하는 데만 쓰고,
   그 결과는 [01_시스템_명세서_초안.md](01_시스템_명세서_초안.md) 에 한국어 산문으로 기록한다.
   구현은 **명세서만 보고** 한다.

3. **기술 스택을 다르게 간다.**
   원본은 PHP 4/5 + 파일 기반 저장.
   우리는 TypeScript + 관계형 DB로 간다. 스택이 다르면 구조적 유사성 주장이 훨씬 약해진다.

4. **밸런스 수치 · 명칭 · 세계관은 새로 설계한다.**
   이건 법적 안전장치일 뿐 아니라, 어차피 상업적 차별점이 된다.

5. **에셋은 전부 신규 제작하거나 상업 이용 가능 라이선스로 조달한다.**

6. **출시 전 IP 전문 변호사의 검토를 받는다.**
   이 문서는 법률 자문이 아니다.

## 3.5 이 문서를 왜 지우지 않는가 (2026-09-12)

단장이 "클린룸 정책을 지워 달라, 어느 정도 참고해도 괜찮다"고 했다. 문서는 남기고 §2 를 넓혔다.
이유는 셋이다.

1. **막고 있던 것이 아니다.** 지난 며칠의 UI 작업(§5.9~§5.14)은 전부 공개 화면을 관찰해
   다시 만든 것이고, 원래부터 §2 의 아이디어 영역이었다. 위에 명문화까지 했으니 이제 더 분명하다.
   실제로 이 문서가 막은 것은 **"원본 소스 코드를 보자"** 한 번뿐인데, 그게 정확히 위험한 지점이다.
2. **이 프로젝트는 상업화를 전제한다.** 원본 이용규정이 상업적 이용을 금지하고, 권리자가
   일방적으로 중단을 요구할 수 있다 (§1). 표현을 가져오면 그 위험이 그대로 넘어온다.
3. **다른 에이전트가 이 문서를 읽는다.** GPT 에게 그림을 시키고 Codex 에게 리소스를 맡기는 지금,
   "남의 그림을 레퍼런스로 올리지 마라"를 적어 둔 곳이 여기다
   ([16](16_캐릭터_아트_주문서.md) §0 이 이 문서를 가리킨다). 지우면 그 고리가 끊긴다.

**그래도 지우기로 하면 지운다** — 단장 프로젝트고 위험을 감수할지는 단장이 정한다.
다만 그때는 "왜 지웠는지"를 여기 대신 적어 두는 편이 낫다.
