# ADR-001. 플랫폼과 기술 스택

- **상태**: 채택 (Accepted)
- **결정일**: 2026-09-09
- **관련 문서**: [01_시스템_명세서_초안.md](01_시스템_명세서_초안.md) 3.4절

---

## 1. 배경

첫 개발에 착수하기 전에 두 가지를 정해야 했다.

1. 웹 게임으로 만들 것인가, 모바일 게임으로 만들 것인가
2. 모바일이라면 어떤 게임 엔진을 쓸 것인가

논의 과정에서 **이 두 질문의 전제 자체가 잘못되었다**는 점이 드러났다.
"웹이냐 모바일이냐"는 기술 선택이 아니라 유통 채널 선택이며,
이 게임의 성격상 하나의 웹 코드베이스로 세 채널(웹 / Google Play / App Store)을 모두 커버할 수 있다.

---

## 2. 결정

### 2.1 아키텍처

```
       [전투 엔진 패키지]
   TypeScript / 순수 함수 / 부수효과 없음
   입력: 편성 + 규칙 + 시드  →  출력: 이벤트 로그
                  │
        ┌─────────┼─────────┬──────────────┐
        ↓         ↓         ↓              ↓
    웹 클라이언트  서버 검증  샌드박스     밸런싱
     (React)              시뮬레이터    배치 스크립트
        │
   ┌────┼────────────┐
   ↓    ↓            ↓
 웹사이트 PWA  Capacitor 래핑 → 스토어
```

### 2.2 스택

| 레이어 | 선택 | 비고 |
|---|---|---|
| 전투 엔진 | TypeScript, 의존성 없는 순수 패키지 | 서버·클라·시뮬레이터가 공유 |
| 수치 표현 | **정수 고정소수점** | 부동소수점 금지 — 리플레이 결정론 확보 |
| 클라이언트 | React + TypeScript | 규칙 에디터가 UI의 대부분이므로 폼 생태계가 중요 |
| 서버 | Node + 관계형 DB | 원본의 파일 기반 저장은 명백한 한계였음 |
| 앱 패키징 | Capacitor (필요 시점에) | 웹앱을 네이티브 껍데기로 감싸 스토어 배포 |
| 전투 연출 (선택) | PixiJS 캔버스 1개 화면 | 필요해지면 그때. 엔진 전체 도입 사유 아님 |

### 2.3 게임 엔진은 사용하지 않는다

Unity, Godot, Unreal 등 **게임 엔진을 도입하지 않는다.**

---

## 3. 근거

### 3.1 왜 게임 엔진을 쓰지 않는가

게임 엔진은 **픽셀 렌더링과 물리 계산**을 위한 도구다. 그런데 이 게임이 화면에 그리는 것은 다음과 같다.

| 화면 | 실제 내용 | 필요 기술 |
|---|---|---|
| 규칙 에디터 (개발 비중 최대) | 드롭다운 + 숫자 입력 + 행 드래그 정렬 | 폼 UI |
| 전투 로그 뷰어 | 스크롤 타임라인 + 텍스트 | 리스트 렌더링 |
| 캐릭터 / 장비 / 스킬트리 | 표, 트리, 툴팁 | 폼 UI |
| 시뮬레이터 리포트 | 통계 표, 그래프 | 차트 |
| 경매장 / 랭킹 | 표, 필터, 페이지네이션 | 폼 UI |

**전투 자체에는 렌더링이 필요 없다.** 순수 계산이고, 결과물은 이벤트 로그다.
로그를 읽기 좋게 보여주는 것이 전부다.

Unity로 이 게임을 만들 경우의 실제 비용:

- 빌드 크기 200MB 이상 (웹 배포 시 치명적)
- 드롭다운 하나 만드는 데 HTML 대비 수 배의 공수
- 텍스트 렌더링 품질과 접근성 열위
- 반복 배포 속도 저하

즉 **도구와 문제의 성격이 정면으로 어긋난다.**

### 3.2 왜 웹을 코어로 두는가

1. **이 장르의 검증된 유저가 이미 웹에 있다.**
   동종 장르의 현존 서버들이 전부 브라우저 기반이며 커뮤니티도 그렇게 형성되어 있다.
   초기 유저 유입 경로가 웹이다.

2. **패턴 공유가 링크로 전파된다.**
   이 게임의 가장 강력한 바이럴 장치는 "내가 짠 패턴 구경해봐"다.
   URL로 즉시 열리는 것과 "앱 설치 후 코드 입력"은 전파력이 자릿수 단위로 차이 난다.

3. **반복 속도.**
   밸런스를 수백 번 고쳐야 하는 게임이다. 웹은 배포가 즉시, 앱은 심사에 하루~며칠이 걸린다.

4. **수수료 구조.**
   웹 직접 결제는 PG 수수료 약 3%, 스토어는 30%다.
   니치 전략 게임의 코어 유저는 웹 결제를 기피하지 않는다. 두 채널 병행 시 매출 구조가 유리하다.

### 3.3 그런데 왜 앱도 필요한가

이 게임의 리텐션 모델은 **행동력 회복 / 레이드 출현 / 콜로세움 쿨타임**에 기반한다.
전부 **푸시 알림이 있어야 작동하는 구조**다.

iOS 사파리의 웹 푸시는 여전히 제약이 크므로, 본격적인 상업화 단계에서는 앱이 필요하다.
Capacitor를 쓰면 코드 재작성 없이 푸시 알림 · 인앱 결제 · 스토어 등록을 확보할 수 있다.

### 3.4 왜 전투 엔진을 별도 패키지로 분리하는가

같은 엔진을 네 곳에서 재사용하기 위해서다.

- **클라이언트**: 전투 즉시 재생
- **서버**: PvP 결과 검증 (클라이언트를 신뢰할 수 없다)
- **샌드박스 시뮬레이터**: 행동력 소모 없이 N회 대전 → 승률 리포트 (원본에 없던 핵심 기능)
- **밸런싱 배치**: 수천 회 대전을 돌려 스킬/장비 밸런스 검증

이 재사용이 성립하려면 엔진은 **부수효과 없는 순수 함수**여야 하고,
**부동소수점 대신 정수 고정소수점**을 써야 한다.
비동기 PvP에서 서버와 클라이언트의 리플레이가 한 프레임이라도 갈리면 신뢰가 무너진다.

## 4. 검토했으나 채택하지 않은 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| **Unity** | 이 프로젝트에 명백한 오버킬. 빌드 크기, 폼 UI 생산성, 반복 속도 전부 불리 |
| **Godot 4** | 무료·MIT·경량이라는 장점은 있으나, Control 노드로 밀도 높은 폼을 구성하는 생산성이 HTML에 크게 못 미침 |
| **Flutter** | 폼 UI와 크로스플랫폼 완성도는 우수. 실질적 2순위. 다만 웹 배포 품질과 링크 공유 특성에서 열위 |
| **React Native** | 웹 코드 재사용률이 Capacitor보다 낮음. 굳이 선택할 이유 없음 |
| **모바일 네이티브 전용** | 링크 기반 패턴 공유라는 최대 바이럴 장치를 포기하게 됨 |

## 5. 결과와 부담

### 5.1 얻는 것

- 플랫폼 확정을 **지금 하지 않아도 된다.** 웹으로 만들면 선택지가 열린 채로 남는다
- 하나의 코드베이스로 3개 채널 대응
- 시뮬레이터 · 서버 검증 · 밸런싱 도구가 엔진 분리의 부산물로 따라온다
- 즉시 배포 가능한 반복 사이클

### 5.2 감수해야 할 것

**최대 리스크: 화면 크기.**

규칙 에디터는 정보 밀도가 높다. 6인치 화면에서 `조건 + 임계값 + 스킬` 10줄을 편집하는 것은
고통스러울 수 있다. 이것은 기술이 아니라 **UX 설계로 풀어야 할 문제**다.

- 모바일: 규칙 목록은 요약 카드로 표시, 편집은 바텀시트로
- 데스크톱: 전체 테이블 인라인 편집
- **처음부터 모바일 폭을 기준으로 설계하고 데스크톱에서 넓힌다.** 반대 순서는 실패한다

→ **M1에서 가장 먼저 검증할 항목**: 규칙 에디터가 폰에서 쓸 만한가?
여기서 답이 안 나오면 그 시점에 웹(데스크톱) 전용으로 범위를 좁힌다.

### 5.3 규제 관련 확인 사항

상업용 게임은 게임물관리위원회 등급분류가 필요하다.
구글·애플·스팀은 자체등급분류사업자이므로 스토어를 통하면 그쪽에서 처리되지만,
**웹으로 직접 서비스할 경우 GRAC에 직접 신청**해야 한다.

절차와 비용이 채널마다 다르므로 **수익화 시점 이전에 반드시 확인**할 것.
규정은 변경될 수 있으므로 실제 출시 직전 재확인이 필요하다.

---

## 6. 이 결정을 재검토해야 할 신호

다음 중 하나라도 발생하면 이 ADR을 다시 연다.

- M1에서 모바일 규칙 에디터 UX가 끝내 성립하지 않을 때 → 웹 전용으로 축소
- 전투 관전 연출이 게임의 핵심 셀링 포인트로 승격될 때 → PixiJS 도입, 그래도 엔진 전체는 재검토 대상
- 웹 채널의 유저 획득 비용이 스토어보다 현저히 높다고 판명될 때 → 앱 우선으로 무게 이동
- 실시간 PvP를 도입하기로 할 때 → 결정론 엔진 전제는 유지되나 네트워크 계층 재설계 필요
