## 1. 이 게임이 무엇인가

**플레이어는 전투를 조작하지 않는다.**

전투 전에 단원마다 **교전 수칙**을 적는다. "이런 상황이면 이 기술을 써라"를 순서대로 적은 목록이다.
출전 버튼을 누르면 전투가 처음부터 끝까지 자동으로 굴러가고, 플레이어는 그 결과를 보고 수칙을 고친다.

실력의 척도는 반사신경이 아니라 **설계 능력**이다. 이 문장이 모든 설계 판단의 기준이다.

```
수칙을 짠다 → 출전 → 전투 로그·연출로 결과를 본다 → 무엇이 어긋났는지 읽는다 → 고친다
```

세계관은 판타지 **용병단**이고, 플레이어는 단장이다. 전투 중 지시를 못 하는 이유는 "교전 수칙" 이라는 설정으로 감쌌다.
톤은 건조한 유머. 자세한 것은 [03_세계관_톤.md](03_세계관_톤.md).

## 2. 용어 사전

여기 나오는 말은 코드·UI·문서에서 **같은 뜻으로만** 쓴다.

| 말 | 뜻 |
|---|---|
| **단원 / 캐릭터** | 플레이어가 보유한 용병 하나. 최대 30명 |
| **편성** | 6칸 판(후열 3 · 전열 3)에 단원을 세우는 것. 출전은 5명까지 |
| **전열 / 후열** | 앞줄 / 뒷줄. 적은 기본적으로 전열을 때린다 |
| **엄호** | 전열이 후열 대신 맞아 주는 것. 조건부(HP 30% 이상일 때 등) |
| **교전 수칙 (수칙)** | 한 단원의 행동 규칙 목록 |
| **패턴** | 수칙의 한 줄. `조건 → 스킬 (N회만)`. 위에서부터 평가해 **처음 참인 줄 하나**만 실행 |
| **패턴 칸 수** | 한 단원이 가질 수 있는 패턴 줄 수. **지능(INT)이 정한다**. 기본 4, INT 10/20/35/50/70 마다 +1 |
| **조건** | 패턴의 왼쪽. 원자 22종을 AND/OR/NOT 으로 묶는다 (깊이 3 제한) |
| **우물쭈물** | 모든 패턴이 거짓이라 아무것도 못 하고 차례를 넘기는 것 (`ruleExhausted`) |
| **시전 (선딜)** | 강한 기술의 준비 시간. 준비 중에는 **끊길 수 있다** — 이 게임의 시그니처 메커니즘 |
| **경직 (후딜)** | 기술을 쓴 뒤 다음 차례가 늦어지는 것 |
| **특성** | 장비·전직이 주는 수동 효과. "단순 +공격력"은 만들지 않는다 — 스탯이 할 일이다 |
| **원형 (archetype)** | 몬스터 분류 8종: 잡몹 · 돌격 · 방벽 · 사격 · 주술 · 독 · 다수 · 보스 |
| **전투 / 모험** | 전투 = 지역 반복. 모험 = 상대 고정 + 재도전 대기·횟수·열쇠·요일 제한, 보상 큼 |

## 4. 엔진 불변식 — 이걸 깨면 게임이 망가진다

1. **완전 결정론.** 같은 입력(시드 + 편성)은 항상 같은 전투 결과를 낸다. 전투 기록을 시드만으로 재생하는 기능이 여기 의존한다.
2. **엔진은 `Math.random` 과 `Date` 를 쓰지 않는다.** ESLint 규칙으로 막혀 있다. 난수는 시드 PRNG(`rng.ts`), 시간 판정은 웹에서만 한다.
3. **정수 연산만.** 부동소수점 없음. `isqrt`(정수 제곱근), `pctOf`(백분율) 같은 헬퍼를 쓴다.
4. **콘텐츠는 데이터다.** 새 스킬·몬스터·지역을 만들 때 `battle.ts` 를 고치지 않는다. 데이터 파일에 한 줄 추가한다.
   기존 효과 프리미티브로 표현이 안 되면 그때 엔진에 **프리미티브를 추가**한다 (개별 스킬 하드코딩 금지).
5. **엔진은 DOM·React·브라우저 API를 모른다.** 순수 함수 패키지다.

## 5. 전투가 어떻게 굴러가나 (요약)

- 각 캐릭터가 **행동 게이지**(0~1000)를 속도에 비례해 채운다. 1000이면 행동.
- 자기 차례에 **수칙을 위에서부터** 평가한다. 처음 참인 줄의 스킬을 쓴다. 전부 거짓이면 우물쭈물.
- 스킬을 못 쓰는 경우(SP 부족 · 대상 없음 · 침묵 · 재사용 대기 · 무기 불일치 · **미습득**)에는 그 줄을 건너뛰고 다음 줄로 간다.
- 선딜이 있는 기술은 예약되고, 다음 차례에 발동한다. 그 사이 피해를 받으면 **끊긴다**.
- 한쪽이 전멸하거나 행동 300회가 지나면 끝난다.
- 결과는 **이벤트 배열**로 나온다. 웹은 이걸 접어서 스테이지 연출·타임라인·패배 진단으로 보여준다.

## 7. 작업 규칙

```bash
npm install
npm run dev            # http://localhost:5173
npm test               # 엔진 테스트 (결정론 골든 테스트 포함)
npm run lint           # Math.random / Date 사용 금지 검사
npm run typecheck --workspace=@webrpg/web
```

- 작업 브랜치는 **develop**. 푸시하면 자동 배포된다
- **콘텐츠를 바꾸면 테스트로 고정한다.** 예: 훈련 과제는 "기본 수칙은 지고 정답은 이긴다"를 시드 10개로 확인한 것만 나간다.
  지역 난이도도 "권장 하한에서 40% 이상, 상한에서 60% 이상"으로 고정되어 있다
- **결정을 문서에 남긴다.** 왜 그렇게 했는지가 숫자보다 중요하다
- 커밋 메시지는 한국어. 무엇을 왜 바꿨는지 쓴다

## 8. 이 게임의 설계 원칙 (판단이 갈릴 때 기준)

1. **선택이 있어야 한다.** 자원이 넉넉해서 결국 전부 갖게 되면 그건 선택이 아니다.
2. **빌드의 정체성은 수칙이 만든다.** 스킬을 8개 배워도 패턴 칸이 4개면 넣을 수 있는 건 4개다.
3. **몬스터가 교재다.** 몬스터도 플레이어와 같은 수칙 시스템으로 움직인다. 지역이 깊어질수록 상대 수칙이 정교해지고,
   그것을 읽는 것이 학습이 된다.
4. **"왜 졌는가"를 알려준다.** 원본의 가장 큰 약점이 13,000px짜리 텍스트 로그였다. 우리는 연출 + 타임라인 + 진단 두 줄.
5. **단순 수치 강화는 스탯이 한다.** 특성·장비는 수칙 설계와 맞물리는 것만 만든다.
6. **뽑기는 하나뿐이고 유료 재화와 절대 연결하지 않는다** (제작 시 특성 30%).
