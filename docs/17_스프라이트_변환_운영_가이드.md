# 스프라이트 변환 운영 가이드 — AI 가 그린 시트를 게임에 넣는 절차와 함정

- **작성일**: 2026-09-12. 직업 5종을 실제로 변환하면서 부딪힌 문제와 고친 방식을 그대로 적었다
- **누가 읽나**: 이미지 생성 AI 가 만든 PNG 시트를 받아 `.px` → `.svg` 로 만들고 검수하는 사람·에이전트 (Codex 포함)
- **앞 문서**: [15](15_전투_스프라이트_규격.md) 는 결과물의 규격, [16](16_캐릭터_아트_주문서.md) 은 AI 에게 주문하는 법. 이 문서는 **받은 뒤**의 일이다
- **한 줄 요약**: 변환기는 초안을 만든다. **눈으로 시트를 보고, 콘솔 숫자를 읽고, 잘못된 것을 찾아내는 것이 이 일의 본체다**

---

## 0. 절대 규칙 (다른 문서와 같다. 다시 쓰는 이유는 이 문서만 받을 수 있기 때문)

1. **원본 PNG 는 `assets/` 안에 두지 않는다.** `assets/` 는 Vite `publicDir` 이라 그 안의 모든 파일이 GitHub Pages 배포에 실린다. 원본 한 장이 1.2MB 다. **`art-source/units/<키>-source.png`** 에 둔다
2. **`.svg` 를 직접 고치지 않는다.** `node assets/build-units.mjs` 가 다음 빌드에 덮어쓴다. 고칠 것은 `.px` 다
3. **만든 파일은 전부 [`assets/README.md`](../assets/README.md) 원장에 기록한다.** AI 로 만든 것은 어떤 도구인지, 입력으로 무엇을 올렸는지까지. 기록 없는 파일은 커밋하지 않는다
4. **남의 그림을 AI 에게 올리지 않는다.** 화풍 참조는 우리가 만든 `assets/units/warrior-sheet.png` 같은 우리 소유물만

## 1. 절차 — 명령 네 줄

```bash
# 0. 받은 PNG 를 제자리에
mv ~/Downloads/rogue.png art-source/units/rogue-source.png

# 1. PNG → .px 초안 (가로 3칸)
node assets/png-to-px.mjs art-source/units/rogue-source.png rogue 3

# 2. .px → .svg (assets/units 의 모든 .px 를 한 번에 굽는다)
node assets/build-units.mjs

# 3. 검수용 시트 PNG (10배 확대, 포즈 3칸 나란히)
node assets/px-to-png.mjs rogue 10
```

그리고 **반드시**:

4. `assets/units/rogue-sheet.png` 를 열어 눈으로 본다 (아래 3절 체크리스트)
5. `npm run dev` → 전투 탭 → 출전 → 실제 화면에서 다른 캐릭터 옆에 서 있는 것을 본다
6. `assets/manifest.json` 의 `units` 에 한 줄, `assets/README.md` 원장에 네 줄 (source / px / svg / sheet)

`png-to-px.mjs` 는 `manifest.json` 에서 그 캐릭터의 `color` 를 읽어 대표색으로 쓴다. **manifest 에 키가 없으면 변환기가 멈춘다** — 새 몬스터라면 manifest 에 먼저 넣는다.

## 2. 콘솔 출력 읽는 법

변환기는 포즈마다 한 줄씩 숫자를 낸다. **이 숫자를 읽지 않고 넘어가면 나중에 화면에서 발견한다.**

```
pose0: 원본 488×613 → 키 52줄, 발에서 왼쪽 22 · 오른쪽 20칸
pose1: 원본 507×613 → 키 52줄, 발에서 왼쪽 21 · 오른쪽 23칸
pose2: 원본 708×602 → 키 52줄, 발에서 왼쪽 22 · 오른쪽 39칸  (상자 밖으로 오른쪽 16칸)
격자 64×64, 상자 (0,0) 은 격자 (0, 0) (@origin 0 0)
```

| 항목 | 정상 | 이상하면 |
|---|---|---|
| `pose0` 의 키 | **항상 52줄** (배율의 기준이 대기 포즈다) | 52 가 아니면 변환기 버그다 |
| `pose1` `pose2` 의 키 | 45~65 사이. 치켜든 포즈가 더 크다 | 대기보다 훨씬 작으면(40 이하) 그 칸이 잘못 잘렸다 → 4절 A |
| 발에서 왼쪽/오른쪽 | 대기 포즈는 15~25 사이 | 한쪽만 40 넘으면 옆 포즈 조각이 붙어 온 것 → 4절 A |
| 상자 밖 오른쪽 | 찌르기·활에서 5~20 | 30 넘으면 원본이 지나치게 뻗은 것. 화면에서 이웃 칸을 덮는다 → 재주문 검토 |
| 상자 밖 위 | 치켜든 지팡이에서 0~5 | 8 넘으면 위 칸의 체력 바를 가린다 → 재주문 검토 |
| 상자 밖 왼쪽 | 0~2 | 5 넘으면 대기 포즈가 왼쪽으로 치우쳐 있다 (망토 등). 화면에서 확인 |
| 색 종 | 8~11 | 11 이 꽉 차면 원본이 팔레트 밖 색을 많이 썼다. 시트에서 색이 이상하게 뭉친 곳을 찾는다 |

## 3. 시트 검수 체크리스트 — 하나라도 걸리면 4절로

`<키>-sheet.png` 를 열고 본다. 10배라 픽셀이 하나하나 보인다.

- [ ] **세 칸의 발바닥이 같은 높이**에 있다 (아래에서 4번째 줄)
- [ ] **세 칸의 몸통 크기가 같다.** 머리 크기를 비교하면 빠르다
- [ ] 세 번째 칸의 **무기 끝이 온전하다.** 시트의 오른쪽 끝에서 잘린 것처럼 평평하면 안 된다
- [ ] 칸과 칸 사이에 **떨어진 조각**이 없다 (옆 포즈의 망토·무기 끝)
- [ ] 발 아래에 **먼지 같은 점**이 없다
- [ ] **눈이 읽힌다.** 2×3 픽셀 덩어리. 뭉개졌으면 손으로 찍는다 (5절)
- [ ] **외곽선이 끊기지 않았다.** 특히 활줄·지팡이 같은 가는 선
- [ ] 다른 캐릭터의 시트와 나란히 놓았을 때 **키와 발높이가 같다** (`warrior-sheet.png` 와 비교)

## 4. 겪은 문제와 고친 방식 — 같은 증상이 나오면 여기부터

직업 5종을 넣으면서 실제로 부딪힌 순서다. 변환기는 이미 고쳐져 있지만, **왜 그렇게 되어 있는지** 알아야 다음 문제를 고칠 수 있다.

### A. 세 번째 포즈가 잘리고, 칸 사이에 조각이 남는다

**증상**: 시트 3칸의 무기 끝이 평평하게 잘림. 2칸과 3칸 사이에 세로 막대 같은 조각.
**원인**: 시트를 **가로 3등분**으로 잘랐다. AI 는 포즈를 균등하게 놓지 않는다. 도적 원본에서 3칸 망토가 2/3 경계보다 왼쪽에서 시작해, 그 조각이 2칸에 들어가고 3칸은 왼쪽이 깎였다.
**수정**: 등분하지 않고 **비어 있는 열**에서 나눈다 (`findCells`). 그림이 있는 열의 연속 구간을 찾고, 좁은 틈(폭의 1.5%)은 같은 포즈로 이어 붙이고, 넓은 것 3개를 고른다.
**남은 함정**: 두 포즈가 실제로 맞닿아 있으면(빈 열이 없으면) 등분으로 물러선다. 콘솔에 경고가 난다. 그 시트는 재주문한다 — "칸 사이를 넉넉히 띄워 달라".

### B. 찌르기 포즈에서 몸이 왼쪽으로 밀리고, 전체가 작아진다

**증상**: 3칸만 몸이 왼쪽에 있다. 세 칸 모두 키가 40줄 안팎으로 작다.
**원인**: 경계 상자의 **가운데**를 x=24 에 맞췄다. 찌르기는 무기 때문에 상자가 넓어져 몸이 밀린다. 그리고 그 넓이가 48칸에 들어가도록 배율을 줄이니 세 칸이 다 작아졌다.
**수정**: 정렬 기준을 **발**로 바꿨다. 상자 아래쪽 12% 줄의 가로 중심을 x=24 에 놓는다. 뻗은 무기는 그 위에 없어서 영향이 없다. 배율은 폭을 보지 않는다 (아래 C·D).

### C. 뻗은 무기가 48칸을 넘친다

**증상**: 발을 x=24 에 놓으면 찌르기 단검이 x=47 을 넘는다 (도적 45칸).
**선택지**: ① 잘라 낸다 ② 배율을 줄인다 ③ 캔버스를 넓힌다 ④ **넘치게 둔다**.
①은 무기가 뭉툭해지고, ②는 몸이 작아지고, ③은 5명이 한 줄에 서는 폰 화면에서 폭이 모자란다.
**수정**: ④. **상자(48×64)와 격자를 분리**했다. 격자는 필요한 만큼 넓히고 `.px` 머리에 `@canvas 48x64` 와 `@origin <x> <y>` 를 적는다. 컴파일러는 viewBox 를 상자로 두고 rect 좌표에서 원점을 뺀다. CSS 가 `overflow: visible` 이라 상자 밖도 그려진다. 찌르기가 적 쪽으로 튀어나가는 모양이 되어 오히려 낫다.
**대가**: 넘친 부분이 이웃 칸을 덮을 수 있다. 오른쪽 20칸까지는 괜찮았다. 2절 표의 한계를 넘으면 재주문.

### D. 한 캐릭터만 유난히 크다

**증상**: 전투 화면에서 도적만 다른 넷보다 크다.
**원인**: 배율을 **가장 높은 포즈**로 정했다. 마법사·전사는 치켜든 무기가 60줄을 차지해 몸이 48줄로 줄고, 대기 포즈가 가장 높은 도적만 몸이 60줄이 됐다.
**수정**: 배율의 기준을 **대기 포즈(1칸)의 키 = 52줄**로 고정했다. 치켜든 무기는 상자 위로 넘친다 (C 와 같은 방식, `@origin` 의 y). 위 8줄이 여유고 그 이상은 넘침이다.
**주문에 미치는 영향**: 1칸에서 무기를 머리 위로 들고 있으면 그 캐릭터만 작아진다. **1칸은 반드시 무기를 내리거나 세워 든 자세**여야 한다 (docs/16 에 반영).

### E. 발이 떠 있고, 발 아래에 점이 흩어져 있다

**증상**: 발바닥이 y=59 보다 위에 있다. 그림자 아래에 먼지 같은 점.
**원인**: AI 출력물은 발 아래에 얇은 잡티가 흩어져 있다. 이게 경계 상자에 들어가 "발"로 잡혀 진짜 발이 위로 올라갔다.
**수정**: 경계 상자·칸 나누기·발 위치 판정에는 **침식한 마스크**를 쓴다 (3×3 이웃이 전부 그림인 픽셀만). 얇은 잡티는 사라진다. 색을 뽑을 때는 원본을 본다. 변환 뒤에도 16픽셀 이하 고립 덩어리는 지운다 (`removeSpecks`).
**남은 함정**: 활줄처럼 진짜로 가는 선도 침식에서 사라진다 — 상자 계산에서만 빠지는 것이고 그림에는 남는다. 다만 1픽셀 선은 축소 과정에서 끊길 수 있다 (5절).

### F. 원본 PNG 가 배포에 실렸다

**증상**: `assets/units/` 에 `-source.png` 5장, 5.7MB.
**원인**: `assets/` 가 Vite `publicDir` 이라 그 안은 전부 배포된다.
**수정**: `art-source/units/` 로 옮겼다. 원장에는 그대로 기록한다.

### G. 컴파일러가 두 방식을 섞어 받았다

**증상**: 한 `.px` 에 `arm0` 과 `pose0` 이 함께 있으면 팔이 두 겹으로 그려진다.
**수정**: `build-units.mjs` 가 막는다. 부위 분리(`body`·`head`·`arm0/1/2`)는 손으로 그릴 때, 전신 포즈(`pose0/1/2`)는 AI 시트를 변환할 때. **AI 시트는 항상 전신 포즈다** — AI 에게 부위를 나눠 그리게 하면 칸마다 어깨 위치가 달라 갈아 끼울 때 팔이 순간이동한다.

## 5. `.px` 를 손으로 고치는 법

변환 결과는 초안이다. 다음은 손으로 고치는 것이 정상이다.

| 무엇 | 어떻게 |
|---|---|
| 눈이 뭉개짐 | 얼굴 자리에 `k` 로 2×3 덩어리를 찍고 왼쪽 위 한 칸을 `w` 로. 세 포즈 모두 같은 위치에 |
| 활줄·지팡이가 끊김 | 끊긴 칸을 원래 색 문자로 이어 준다. 대각선은 계단으로 |
| 외곽선이 끊김 | 끊긴 칸을 `k` 로 |
| 색이 이상하게 스냅됨 (예: 어두운 보라가 `L` 가죽색으로) | `@palette` 에 문자를 하나 더 정의하고 (`p #3a2f55` 같이) 그 칸들을 바꾼다. 12색 안에서 |
| 한 포즈만 발높이가 다름 | 그 레이어의 줄을 통째로 위/아래로 옮긴다 (줄 하나 지우고 반대쪽에 빈 줄 하나 넣기) |

고친 뒤 `node assets/build-units.mjs` 와 `node assets/px-to-png.mjs <키> 10` 을 다시 돌려 확인한다.
**`.px` 를 고쳤으면 다시 변환기를 돌리지 않는다** — 돌리면 덮어쓴다. 변환기를 다시 돌려야 할 이유가 생기면(원본 교체) 손으로 고친 것은 사라진다고 알고 하라.

## 6. 재주문할 것인가, 손으로 고칠 것인가

| 상황 | 판단 |
|---|---|
| 세 칸의 얼굴·복장이 다르다 | **재주문.** 손으로 못 맞춘다 |
| 정면을 똑바로 본다 | **재주문.** 3/4 로 |
| 1칸(대기)에서 무기를 머리 위로 들었다 | **재주문.** 배율 기준이 무너진다 (4절 D) |
| 무기가 오른쪽 30칸 · 위 8칸 넘게 뻗는다 | **재주문.** 이웃 칸을 덮는다 |
| 칸 사이에 빈 열이 없어 등분으로 물러섰다 | **재주문.** "칸 사이를 띄워 달라" |
| 눈·활줄·외곽선 몇 칸 | 손으로 (5절) |
| 색이 한두 군데 이상하다 | 손으로 (5절) |
| 발 아래 점 몇 개가 남았다 | 손으로. `.px` 에서 `.` 으로 |

재주문할 때는 docs/16 의 주문문에 **문제가 된 항목을 한 줄 덧붙인다.** 주문문 자체를 고칠 만하면 docs/16 을 고친다 — 다음 사람이 같은 함정에 빠지지 않게.

## 7. 도구 셋의 관계

```
art-source/units/<키>-source.png     AI 가 준 원본. 배포 밖. 원장에 기록
        │  node assets/png-to-px.mjs <원본> <키> 3
        ▼
assets/units/<키>.px                  문자 격자. 손으로 고치는 정본
        │  node assets/build-units.mjs
        ▼
assets/units/<키>.svg                 화면이 쓰는 것. 직접 고치지 않는다
        │  node assets/px-to-png.mjs <키> 10
        ▼
assets/units/<키>-sheet.png           검수용 + 다음 주문의 화풍 참조
```

- `png-to-px.mjs`: PNG 디코드(외부 라이브러리 없음) → 빈 열 분할 → 침식 마스크 → 발 기준 정렬 → 대기 포즈 52줄 배율 → 넘침 격자 → 팔레트 스냅 → 잡티 제거
- `build-units.mjs`: `@canvas`/`@origin` 을 읽어 viewBox 는 상자, rect 는 원점 보정. 부위/전신 두 방식을 받되 섞으면 멈춤
- `px-to-png.mjs`: 격자 전체를 그린다 (상자 밖 포함). 그래서 시트에서 넘친 부분이 그대로 보인다

세 도구 모두 `node:zlib` 외에 의존이 없다. 고칠 때도 의존을 추가하지 않는다.
