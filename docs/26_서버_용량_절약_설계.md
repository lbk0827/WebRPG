## 1. 용어

| 용어 | 뜻 |
|---|---|
| 저장 | 계정마다 한 줄(`saves` 테이블)에 들어가는 게임 진행 JSON 통째 |
| 쓰기 횟수 | 브라우저가 서버에 저장을 보내는 횟수. 무료 요금제에서는 용량보다 이쪽이 먼저 한계에 닿는다 |
| 전송량(egress) | 서버가 내보내는 데이터 양. 로그인 때 저장을 한 번 읽는 정도 |
| 시드 재생 | 엔진이 결정론이라 시드 + 양 팀 편성만 있으면 같은 전투를 그대로 다시 계산해 보여 주는 것 |

## 2. 측정 (2026-09-15, `newGame` + 상한까지 채운 가상 저장의 JSON 길이)

| 경우 | 크기 |
|---|---|
| 새 게임 직후 | 0.8 KB |
| 단원 1명 | 0.5 KB |
| 수칙 프리셋 1개 | 0.2 KB |
| **전투 기록 1개** (양 팀 편성 통째) | **5.2 KB** |
| 끝까지 키운 계정 — 단원 30(`MEMBER_MAX`) · 기록 12(`LOG_MAX`) · 프리셋 20(`RULE_PRESET_MAX`) · 장비 200 | **약 95 KB** (그중 전투 기록 약 62 KB) |

- 상한이 있어서 오래 해도 약 100 KB 에서 멈춘다.
- 무료 DB 500 MB 기준 끝까지 키운 계정만으로 약 5,000명, 실제 분포(대부분 중도 이탈)면 1만 명 이상. DB 는 큰 JSON 을 자동 압축(TOAST)해서 디스크는 더 적게 쓴다. Supabase 기본 시스템 데이터 수십 MB 는 뺀다.
- **먼저 닿는 한계는 쓰기 횟수**: B 단계 첫 구현은 2초마다 저장 통째(최대 100 KB)를 다시 쓴다. 동시 접속 수백 명이면 무료 서버 성능이 먼저 모자란다.
- 사용량 확인: Supabase 대시보드 → Organization → Usage (또는 프로젝트 Reports). DB 70% 에 가까워지면 docs/25 §8.1 미접속 정리.

## 3. 개선 후보와 판단

| # | 방법 | 효과 | 부담 | 판단 |
|---|---|---|---|---|
| 1 | **바뀐 게 없으면 안 보내기 + 간격 늘리기** (중요한 순간은 즉시) | 쓰기 횟수 크게 감소 | 몇 줄. 체감 차이 없음 | **지금** |
| 2 | **전투 기록을 서버 저장에서 빼기** | 저장 크기 약 65% 감소 (최대 95 → 약 33 KB) | 다른 기기에서 "최근 전투" 목록이 비어 보임 | **지금** |
| 3 | 공유할 때만 기록 하나를 서버에 (링크 복사) | 공유 기능이 생기고 용량은 공유한 만큼만 | 테이블 · 재생 화면 · 버전 표시 | **다음** (§4) |
| — | 기본값과 같은 수칙·설정 생략 | 작음 | 복잡 · 버그 위험 | 안 함 |
| — | 필드 이름 줄이기 · 브라우저 압축 | 작음 (DB 가 이미 압축) | 나중에 랭킹이 저장을 못 읽음 | 안 함 |
| — | 바뀐 부분만 보내기 | 중간 | 복잡 | 동시 접속 수백 명 때 재검토 |

이미 되어 있는 것: 계정당 저장 한 줄(덮어쓰기) · DB 자동 압축 · 서버 읽기는 로그인 때 한 번(실시간 동기화 없음) · 기록 12 · 단원 30 · 프리셋 20 상한.

전투 기록이 쓰이는 곳(코드 확인): 본부 "최근 전투" 목록과 다시보기뿐. 지역 해금(`regionWins`) · 승수(`battles` · `wins`) · 보상은 기록과 따로 저장된다 → 서버에서 빼도 진행에는 영향 없음.

## 4. 참고: HOF · 제로식의 전투 로그 (HOF 소스 관찰, 제로식은 같은 계열로 추정)

| 항목 | HOF |
|---|---|
| 위치 | 서버 폴더에 파일. 일반 · 랭크 · 유니온 따로 |
| 내용 | **화면에 출력된 전투 전체**를 그대로 + 머리말(팀 이름 · 인원 · 평균 Lv · 승패 · 턴 수) |
| 소유 | 사용자별이 아니라 **서버 전체 공용** 목록 |
| 상한 | 종류마다 **최근 100개**, 넘치면 오래된 것부터 삭제 |
| 링크 | 파일 이름(시각 번호)이 주소 — 누구나 열람 |

제로식에도 공개 "전투로그" 메뉴와 설정 "로그 공개"가 있다 (docs/11 §5.1).

**서버에 두는 이유**
1. 전투를 서버가 계산한다 — 브라우저에 엔진이 없으니 다시 보려면 서버가 결과를 들고 있어야 한다.
2. 공유 · 커뮤니티 — 고수의 수칙 구경, 게시판 공략, 랭크전 상대 연구가 이 장르의 재미.
3. 분쟁 · 부정 확인 — 운영자가 증거로 본다.

**우리와 다른 점**: 우리 엔진은 결정론이라 로그 통째 대신 시드 + 편성(약 5 KB)이면 어디서든 똑같이 재생된다. HOF 는 통째 저장이지만 서버 전체 100개로 용량을 묶었다.

## 5. 결정 (권장안)

### 5.1 지금 — 쓰기 줄이기 · 기록 빼기
- 마지막으로 보낸 내용과 같으면 보내지 않는다.
- 모아 보내는 간격 2초 → **8초**. 대신 **전투가 끝났을 때(`battles` 변화) · 금이 바뀌었을 때(구매 · 강화 · 고용 · 보상) · 단원 수가 바뀌었을 때 · 탭을 숨길 때 · 로그아웃할 때**는 즉시.
- 전투 기록(`log`)은 서버 저장에서 빼고 **그 브라우저에만** 계정별로 둔다.

### 5.2 다음 — 공유 링크 (§3 의 3)
- 전투 기록에 **"링크 복사"** → 그 기록 하나만 공유 로그 테이블에 올리고 `…/WebRPG/?log=<id>` 링크. 링크를 연 브라우저가 엔진으로 재생, 로그인 없이 볼 수 있다.
- 용량: **계정당 최대 20개**(넘치면 오래된 것부터) **+ 30일 자동 만료** 둘 다.
- **밸런스 패치 대책**: 공유 로그에 데이터 버전을 함께 저장하고, 지금 버전과 다르면 "이전 버전의 전투라 결과가 다를 수 있습니다" 표시. (행동 목록까지 저장하면 정확하지만 개당 용량이 몇 배 — 채택 안 함)
- 필요: 단장이 SQL Editor 에서 공유 로그 테이블 SQL 실행.

### 5.3 나중 — 랭크전 · PvP (docs/25 C 단계)
- 서버가 판정하므로 HOF 처럼 서버에 로그를 남기되 **최근 N개만** 유지.
